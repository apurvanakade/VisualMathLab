# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Visual Math Lab is a Quarto website of interactive, browser-based visualizations of numerical methods. There is no backend and no build tooling beyond Quarto — all interactivity runs client-side via Observable JS (OJS) cells in each page, math.js and Plotly from CDNs, and the **mathviz** library: the shared `window.VM` utilities, the `ojs-*` design-system CSS and the `--vm-*` token defaults. That library lives in [apurvanakade/mathviz](https://github.com/apurvanakade/mathviz) and is installed here as a tagged release. This repo is the site itself: app pages, topic listings and the site-only includes. See the mathviz section below.

## Commands

- `quarto render` — render the whole site into `docs/` (`_quarto.yml` sets `project.output-dir: docs`).
- `quarto render apps/newton-method/index.qmd` — re-renders that page plus any listing/index pages that glob-discover it (its topic index, the homepage) — lighter than a full-site render, but **not** a true single-page render (it's still a multi-file batch job, not something you can point a browser at). For actually isolating one page, use `quarto preview` instead.
- `quarto preview` — local live-reload preview server, and the right tool for rendering/iterating on just one page: it renders (and re-renders on save, via its own mtime-based file watcher) only the page you actually navigate to, not the whole site or its listing pages.
- `npm test` — Node's built-in test runner over the whole repo: `scripts/analytics.test.js`, `scripts/fonts.test.js`, `scripts/registration.test.js` and `scripts/methods.test.js`, the site's own structural tests, plus each method page's `apps/<slug>/method.test.js`, which runs every example the page offers and checks the convergence order its plot reports (see Architecture). The library's tests live and run in mathviz. Requires `npm install` once first.
- `QUARTO_PROJECT_RENDER_ALL=1 scripts/update-mathviz.sh` — force a check for a newer mathviz release now (the pre-render hook does this before every full render anyway; see the mathviz section).
- `npm run verify:analytics` — real-browser test of the analytics consent flow (`_includes/analytics.html` + `_includes/consent.html`): banner display, Allow/No thanks, the footer reopen link, withdrawal, and Do Not Track/Global Privacy Control. Requires `docs/` to already be rendered. Fast to re-run on its own while iterating on consent copy or wiring, without paying for a full-site `npm run verify` crawl.
- `npm run verify` — `quarto render` then a headless-browser pass over **every** rendered page on the site (one load per page: clicks every button, nudges every slider, asserts zero console/page errors, plus two authoring checks — a `.vm-app` on every app page, and an example dropdown that opens on the first example). This is what actually catches a broken `VM.category.fn` call site — `quarto render` alone only catches Pandoc/parse errors, not OJS runtime errors. It's a full-site crawl (all pages, about a minute and a half, four pages at a time — `--jobs N` to change that) — **only run it when the user explicitly asks for it**, not as the default post-edit check. See `.claude/skills/verify/SKILL.md` for the full two-tier verification approach and why it's structured this way.
- `npm run verify -- --changed` — the same crawl over only the pages whose folder differs from `develop` (committed, staged, unstaged or untracked); it falls back to the full site, and says why, when the diff also touches something baked into every page (`_extensions/`, `_includes/`, `_quarto.yml`, the generated `_sidebar.yml`, `apps/_metadata.yml`). Optional, and only for page-scoped changes: when it would fall back to the full site, skip it and let the PR's `pr-check.yml` crawl instead.
- `.github/workflows/pr-check.yml` runs `npm test`, `npm run verify` and `npm run verify:analytics` on every pull request to `develop` (and on `workflow_dispatch`), so the full crawl is also a CI gate, not only an on-demand local check. `CONTRIBUTING.md` points contributors at the targeted `npm run verify -- apps/<slug>/index.qmd` locally and at this check for the rest.

**Default verification for a change scoped to one page**: `quarto preview` the project, then load just that page's URL (it renders on demand, nothing else) and check it there — for a scripted check, drive that same URL with a short one-off Playwright script, asserting zero `console.error`/`pageerror` while exercising its controls (see `.claude/skills/verify/SKILL.md`'s gotchas on why `file://` won't work and what to stub). Don't run the full `npm run verify` crawl locally unless the user asks for it — not even for a new mathviz release or another shared file, whose output lands in every page's `<head>`. `pr-check.yml` runs that crawl on every pull request (see the `ship-pr` skill), so locally a look at a page that uses the changed function is enough.

There is no lint command. `package.json` is dev-only (Playwright for `npm run verify`) — nothing in it is shipped to `docs/` or affects the site's runtime; the site itself still has no bundler and no build step beyond `quarto render`. JS is served as static files, not bundled.

## Source vs. generated output

- **This site is `.qmd` pages plus config.** Edit `.qmd`, `_quarto.yml`, and `_includes/` (which holds only the analytics snippet, its consent banner, the giscus comments include, the homepage's category cloud and the site-wide tag links — deliberately site-specific, see below). Every stylesheet and script that isn't a single page's own, or the tags', lives in mathviz; there is no `styles.css` and no `js/`. **`docs/` is generated** — never edit it by hand; re-render instead. (`.gitignore` ignores `docs/`, though a prior build is still tracked.) **`_extensions/apurvanakade/mathviz/` is the installed mathviz release, not authored here**: the pre-render hook replaces it. Don't edit it. Library changes are pull requests to mathviz. It is committed (a `.gitattributes` rule collapses the diff) so a render works offline. See the mathviz section below.
- **Changes reach `develop` through a pull request, not a direct push** — branch, push, `gh pr create --base develop`, and merge once `pr-check.yml` is green. That PR is the only place CI runs the full crawl: a direct push to `develop` runs no tests, and neither does the push to `main` that deploys, so anything pushed straight to `develop` ships unverified. The one exception is a trivial edit that can't break a rendered page — a typo or wording fix in prose, a comment, or a change to repo-only docs (`CLAUDE.md`, `README.md`, `CONTRIBUTING.md`) — which may be committed on `develop` directly. Anything touching an OJS cell, CSS, `_includes/`, `js/`, `_extensions/`, `_quarto.yml` or a workflow is not trivial, however small. This is a convention, not an enforced rule: `develop` has no branch protection.
- **PR workflow, end to end**: once a change is ready, run the `ship-pr` skill (`.claude/skills/ship-pr/SKILL.md`). It carries the change all the way through without stopping: worktree and branch, PR into `develop`, triage of Copilot's review against this file's conventions (when Copilot is out of credits, a fresh local agent briefed as a maintainer reviews the PR in its place -- `.claude/skills/ship-pr/maintainer-review.md`), `pr-check.yml`, merge, the fast-forward of `main` and cleanup. The rules it follows are the ones in this section and in "Branches and preview" below. When a rule changes, update it in both places.
- **Releasing (`develop` → `main`): fast-forward only.** `develop` is where work lands; `main` is a pointer to the last published state, and pushing it deploys (see below). Release with `git checkout main && git merge --ff-only develop && git push origin main`, then `git checkout develop`. Do **not** squash-merge into `main`: a squash commit records no parent link back to `develop`, so the merge base between the branches never advances — every later merge re-diffs the entire branch from an ancient base and conflicts with content `main` already has (13 squash-merges had frozen the base at a commit 52 commits back, and the last one conflicted across 8 files with zero real divergence). If `--ff-only` is ever refused, the histories have diverged again; reconcile once with `git merge -s ours main` on `develop` (records `main` as an ancestor without changing `develop`'s tree) rather than force-pushing `main`.
- `.github/workflows/publish.yml` renders the site and publishes `docs/` to the `gh-pages` branch automatically on every push to `main`. GitHub Pages serves that branch directly (repo Settings → Pages → "Deploy from a branch", `gh-pages` `/`), so GitHub's own "pages build and deployment" run follows each publish. There is no deploy workflow of ours: a `deploy.yml` triggered by pushes to `gh-pages` existed until 2026-09-28 and never ran once, because a push made with `GITHUB_TOKEN` can't start another workflow and `actions/deploy-pages` needs the Pages source set to "GitHub Actions" anyway.
- **A separate contributor "starter" repo (this site's chrome with no apps, synced from here) was evaluated on 2026-09-20 and rejected.** The full-site render is not the slow step -- the CI publish job (checkout, Quarto install, render all 29 pages, push) takes 42--61 s end to end, a one-time cost after which `quarto preview` is per-page lazy -- and GitHub can't open a pull request between unrelated repositories, so a starter-built app would still need a fork of this repo, a folder copy and the two registrations: a detour, not a shortcut, on top of a second repo, a sync workflow with a PAT and a split `_quarto.yml`. What contributors actually found slow was the pre-PR full crawl; `pr-check.yml` (above) runs that on GitHub instead.

## Branches and preview: one worktree per branch

**Never `git checkout` a branch inside a folder with a running `quarto preview`.** The preview's watcher treats a change to `_quarto.yml`, the generated `_sidebar.yml` or anything under `_includes/`/`_extensions/` as invalidating every page (correctly -- the sidebar and `<head>` are baked into each one), and almost every feature branch touches at least one of those. A checkout rewrites them, so the watcher kicks off a full-site re-render (minutes) on every switch. Per-page laziness applies only to `.qmd` edits.

The fix is to not switch branches in place. `~/Documents/VisualMathLab` is the long-lived **`develop`** checkout and stays on `develop`; every other branch gets its own sibling folder via `git worktree`, with its own untracked `docs/`, `.quarto/`, and preview server on its own port. `git worktree list` shows which folder holds which branch.

There is a second, separate trigger with the same symptom: **on startup, `quarto preview` renders every input whose output in `docs/` is missing or older than the input** (`serveFiles` in Quarto's `serve.ts` compares mtimes; the `--render none` default only means "don't re-execute code", not "don't render"). So a brand-new worktree, whose `docs/` is empty, pays one full-site render the first time its preview starts -- expected, and once per worktree, not per switch. After that, startups only re-render what is stale. This is also why killing the preview *before* a checkout doesn't help much: the checkout still bumps the mtime of every `.qmd` that differs, and the next startup re-renders all of them.

1. **New feature branch**: `git worktree add -b app/<slug> ../VisualMath-<slug> develop`, then in that folder `quarto preview --port <unused port> --no-browser`. Use `4200` for develop and count up from `4201` for features -- one preview per worktree, never two in the same folder.
2. **Existing branch**: same command without `-b`. A branch can be checked out in only one worktree at a time; if git refuses, `git worktree list` shows where it already lives.
3. **Switching branches**: `cd` to the other folder (or switch browser tabs to its port). Nothing is rewritten, so nothing re-renders.
4. **Tests in a worktree**: `node_modules/` is per-folder, so run `npm install` once there (or `ln -s ../VisualMathLab/node_modules node_modules` -- `package.json` is identical across branches) before `npm test`/`npm run verify`.
5. **Landing**: push the branch, open a PR into `develop`, merge it once `pr-check.yml` passes, then `git pull` in the develop folder (see "Changes reach `develop` through a pull request" above). Its preview will do one full re-render if the merge touched the project-level files above -- once per merge, not per switch.
6. **Cleanup**: stop that worktree's preview, then `git worktree remove --force ../VisualMath-<slug>` and `git branch -d app/<slug>`. `--force` because the folder always holds untracked build output (`docs/`, `.quarto/`, `node_modules`) that a plain `remove` refuses to delete -- check `git status --short` there first for a modified tracked file, which would be unmerged work.

If you ever must checkout or pull in a folder that has a preview, kill the preview first and restart it afterwards. That avoids the watcher's reaction to the project-level files, but the restart will still re-render every page whose `.qmd` the checkout touched (see above) -- there is no way to switch branches in place without paying for what changed.

## Analytics and consent

Usage analytics only — no ads signals, no remarketing, no Google Signals.

- `_includes/analytics.html` is the minimal GA4 snippet (~3kB, vendored from
  [dariusz.wieckiewicz.org](https://dariusz.wieckiewicz.org/en/minimal-google-analytics-4-snippet/)),
  talking straight to the Measurement Protocol v2 endpoint instead of loading
  gtag.js. The file's header comment lists every local deviation from
  upstream; keep that list accurate when re-vendoring a newer version.
- `_includes/consent.html` is the consent banner, plus the gate that actually
  runs the snippet. **Quarto's built-in `cookie-consent:` is deliberately not
  used** — its copy is baked into its bundle and claims the site shows
  personalized content and targeted ads, with a whole "Targeting and
  advertising cookies" section in its preferences center; there is no
  supported way to change those strings, its 34-language switcher would leave
  every other translation making the same false claim, and it weighs 207kB to
  gate a 3kB snippet. Don't reintroduce it.
- **The gate**: analytics.html ships as `<script type="text/plain"
  data-consent="analytics">`, which no browser will execute. consent.html
  re-creates it as a real `<script>` once the visitor allows analytics.
  Assigning to `.type` in place would not work — a script only runs when it is
  inserted. Don't "fix" that `text/plain` type; it is the gate.
- Both are loaded through `include-after-body`, **in that order** — consent.html
  searches the DOM for the script analytics.html emits, and the snippet reads
  `document.body`/`document.title` at call time, so neither belongs in
  `include-in-header`.
- The consent choice lives in `localStorage`, so **the site sets no cookies at
  all**. Global Privacy Control and Do Not Track are honoured as an answer
  already given.
- `privacy.qmd` (linked from the footer, alongside an "Analytics preferences"
  link that reopens the banner) documents exactly what is sent and what is
  stored. **It is a factual claim about the code**: if you change what the
  snippet collects or what is stored, change that page in the same commit.
- The snippet drops the query string from the reported page location. On this
  site a query string is the visitor's own math input (see the URL-shareable
  inputs section below), which doesn't belong in an analytics report and would
  fragment one page into hundreds of addresses.
- **Do Not Track / Global Privacy Control win over the footer link.** The
  snippet returns early on either signal even after consent, so a recorded
  "yes" would measure nothing; the reopened banner therefore says so and
  disables Allow rather than pretending. `privacy.qmd` states the signal
  wins; both test tiers assert it.
- **Third-party requests are part of the privacy surface**, and `privacy.qmd`
  has a "Third-party resources" section that names every host a page loads
  from (`cdn.plot.ly`, `cdn.jsdelivr.net` for math.js and Quarto's MathJax,
  `cdnjs.cloudflare.com` for Quarto's polyfill). the mathviz extension
  emits `<meta name="referrer" content="same-origin">` (`mathviz.referrer` in
  `_quarto.yml`, ahead of its own CDN tags) so none of them sees the
  page path or query string, and fonts are self-hosted (`mathviz.fonts`;
  see the theme section below). Adding a CDN script — in a site include or via a new
  `mathviz:` option — means adding its host to that page; a Tier 1 test
  cross-checks the two by reading both files.
- Covered by both test tiers: `scripts/analytics.test.js` (Tier 1 — structural
  invariants on both files' contents, plus the snippet's client-side logic run
  against a stubbed DOM) and `scripts/verify-analytics.mjs` / `npm run
  verify:analytics` (Tier 2 — the consent gate itself in a real browser, since
  a `text/plain` script only fails to execute there, not in a stub). Update
  both when changing this wiring.

## Comments (giscus)

`_includes/giscus.html` (the third `include-after-body`) appends a giscus thread to every page with a `.vm-app`: a GitHub Discussion in the repo's **General** category, keyed by the page's path. On a split page it is appended to `.vm-split`, so it lands at the end of the prose column; elsewhere at the end of `#quarto-document-content`.

- **It builds giscus's iframe itself instead of loading `giscus.app/client.js`** (or Quarto's `comments: giscus`, which loads client.js). client.js sends the full page address as the widget's `origin` and back link, and the query string is the visitor's math input (see the URL-shareable inputs section) — it would reach giscus.app and the first commenter's inputs would be published in the discussion. The include mirrors client.js's contract instead (widget URL parameters; resize/sign-out/error/`setConfig` messages), which giscus's own framework components also implement, so it is stable. The header comment says what it mirrors; recheck it against client.js if giscus changes behavior.
- Never in embed mode (it returns early on `html.vm-embed`), and the frame is `loading="lazy"`.
- Because `origin` has no query string, a reader leaving the page signed out has its `location.search` kept in sessionStorage (`vml-giscus-return`), and a return from GitHub sign-in (`?giscus=`) reloads the page with it.
- `privacy.qmd`'s "Comments" section names `giscus.app` and `avatars.githubusercontent.com` and the storage entries. `scripts/analytics.test.js` pins those claims; `scripts/verify-pages.mjs` stubs giscus.app in the crawl (an unanswered page with no discussion yet logs 404s); `scripts/verify-analytics.mjs` (section 7) fails an embed page that shows the comments or requests giscus.app.

## Embed mode

Any app page loaded with `?embed=1` renders the app alone — its controls and chart, nothing else on the page — for another site to put in an `<iframe>` (`embed.qmd` documents this for readers; the footer links to it). The pieces:

- **Every app page tags its app**: `<div class="vm-app">` … `</div>` (a raw-HTML div, like the `ojs-panel`/`ojs-chart-block` wrappers) around the controls panel, the slider bar and the main chart block — for a method page, from the first `<div class="ojs-panel">` through the `.ojs-chart-block`'s closing `</div>`. The "Convergence plots"/"Iteration table" callouts, any secondary plot and the prose stay outside: they are exposition, not the app. The wrapper may sit at the top level of the page or under a `##` heading (Quarto wraps a heading's content in a `<section>`; the CSS keeps the chosen block's ancestors visible), but not inside a callout or tabset, whose chrome would then show around it. `//| output: false` helper cells may sit inside or outside it — hidden cells still run. A page with several interactive figures tags each with an `id` (`apps/sperners-lemma-combinatorial-proof/index.qmd`: `triangulation`, `doors`, `boundary`), unique on the page and not colliding with a heading's auto-generated slug; `?embed=<id>` then shows that one, `?embed=1` the first. `npm run verify` fails any app page with no `.vm-app`, so a new page can't forget it.
- The machinery is mathviz's opt-in chrome (`src/chrome/` there), switched on in `_quarto.yml`: `mathviz: {share: {site-url: https://www.visualmathlab.com, embed-docs: embed.html}}` turns on the Share button and, with it, embed mode (`embed.js` + `embed.css`; `embed: true` alone would give embed mode without the button). `site-url` repeats `website.site-url` because a Quarto filter can't see project config.
- `embed.js` is a plain dependency script in `<head>`, so it adds `vm-embed` to `<html>` before `<body>` exists and the chrome never paints; at `DOMContentLoaded` it marks the chosen block `vm-app-active`: the block whose `id` is the `embed` value, else the page's first `.vm-app`. It also wraps `history.replaceState` so the `embed` value survives the URL rewrite every app does from its `committed`/`urlSyncControls` cells. The wrapper matters for a page that builds its query string from scratch (`apps/distribution-relationships/index.qmd`'s `new URLSearchParams()`) rather than from `location.search`; a page should still prefer the latter.
- `embed.css` hides the navbar, sidebar, glass, rail, title block, footer, page navigation, mathviz's mobile warning, report-bug popup and share bar/dialog on `html.vm-embed`, plus any element carrying **`data-vm-embed-hide`** — how a site hides chrome of its own without the library naming it (this site's consent banner has it). It zeroes the fixed-navbar body padding, and hides everything in `#quarto-document-content` that is neither the `.vm-app-active` block, inside it, nor one of its ancestors (a `:has()` rule, so it works at any depth).
- `consent.html` and every mathviz chrome script (sidebar rail, mobile warning, report-bug, share) return early on `html.vm-embed`. Consent's early return is a privacy claim: an embedded app never shows the banner and never runs analytics, even for a visitor with a stored "yes" — `privacy.qmd` says so, `scripts/verify-analytics.mjs` section 7 tests it.
- mathviz's `share.js` injects a **Share** button as the first child of every `.vm-app` block (one per figure, so a multi-app page gets one button per block, each writing the right `embed=<id>`), opening a `<dialog>` with the page's own link (with and without the current inputs) and the `?embed=` `<iframe>` snippet `embed.qmd` documents — a "Keep the current inputs" checkbox (reads `location.search`, which the `committed`/`urlSyncControls` cells keep current) and a frame-height field, defaulting to 900 for a Plotly chart or the block's own measured height otherwise. Links point at the `share.site-url` option; the dialog links `embed-docs` (here `embed.html`). The dialog is created once, on first open, and appended to `document.body` (outside `#quarto-document-content`, like the slider-play popover); `npm run verify`'s button-mashing loop closes any dialog it opens before moving on, since a modal `<dialog>` makes the rest of the page inert. Keep the snippet shape in `share.js` and in `embed.qmd` in sync — mathviz's `src/chrome/share.test.js` covers the pure builders (`VM.chrome.share.embedSrc`, `.buildEmbedSnippet`), not the shape match itself, so a hand-edit to one without the other won't fail a test.
- GitHub Pages sends no `X-Frame-Options`, so nothing server-side is involved. A new piece of mathviz chrome goes in `embed.css`'s hide list; a new element of this site's own gets `data-vm-embed-hide`.
- The embed page is the same page hidden, not a separate render: the whole page still downloads and its hidden OJS cells still run. Negligible at these sizes; if it ever isn't, the next step is a `{{< include >}}` split (fragment + page + embed stub per app), not a second repo.

## Architecture

Each app page (`apps/<slug>/index.qmd`, e.g. `apps/newton-method/index.qmd`) is a self-contained interactive app, built from named OJS cells inside the `.qmd`. A page whose convergence plot reports an order or slope (every Root Finding, Interpolation & Integration and Differential Equations page, and `apps/_template/`) also has two colocated files:

- **`method.js`**, an ES module holding the page's `examples`, the method itself (a plain function of a parsed `f` and numbers, returning `rows`) and, on the slope pages (bisection, fixed-point, `_template`), `convergenceFit`, which decides which points the convergence plot draws and the number its legend reports. The other pages fit with the library instead: an error-vs-n page (integration, both ODE pages, interpolation) calls `VM.numerical.orderFromErrorsVsN(rows, reference, errorKey)`, and Newton and the secant method call `VM.numerical.orderFromSuccessiveErrors(rows, "error", "xNext")`. The `.qmd` imports from `method.js` in one cell (`import {examples, newton} from "./method.js"`); Quarto copies the file next to the rendered page. It touches no DOM and no OJS, and reads the library as `globalThis.VM`, so Node can run it.
- **`method.test.js`**, which runs every example through `method.js` (parsing each formula with the page's own `VM.expressions.*`, from the installed mathviz release via `scripts/load-vm.mjs`) and asserts the order the plot reports: a number within a stated tolerance, "exact", or no fit at all. Each expectation says why that is the right number; where it differs from the textbook order (a corner, a multiple root, a natural spline's end condition, a method still settling at these n), the comment says so.

The test is the point: a convergence plot's legend is a claim about the math, and it used to be checked only by eye. That missed a Newton's-method default that reported order 0.74 (errors at rounding level flattened the fit), diverging runs that reported an order, and ODE examples whose fit over every n reported Euler at order 5. Every fit that reports an order follows two rules: drop errors at rounding level (below about `1e-12` times the size of the value), and fit only the asymptotic part of the run (n ≥ max/2 for an error-vs-n plot, `VM.numerical.orderFromErrorsVsN`; the trailing run of shrinking errors for a successive-error plot, `VM.numerical.orderFromSuccessiveErrors`). The slope pages (bisection, fixed-point, `_template`) fit the whole run: their errors fall to exactly 0 at rounding level, which they already skip (bisection's and fixed-point's tests pin the slope at a large Max). An example whose orders haven't settled by its max gets a larger max, not a looser test. `scripts/methods.test.js` fails a page that reports an order without these two files, and an example that sets a field the page's `exampleFieldSelectors` doesn't list. Other pages keep their logic in the `.qmd`. The cells:

1. `_quarto.yml`'s `filters: [mathviz]` runs the extension's filter on every page, which puts math.js, Plotly, `mathviz.js` and `mathviz.css` into `<head>` — in that order, and *ahead of* everything in `include-in-header` — exposing `window.VM` (see the mathviz section below). The site's `mathviz:` options add the rest as dependencies of their own: the self-hosted fonts, the sidebar rail, the mobile warning, embed mode, Share and report-bug (see the mathviz section). Every page gets all of this for free — no per-page script block is needed, and the site has no script of its own besides the analytics snippet and the giscus comments include.
2. `result` — runs the numerical method with the current inputs (e.g. Newton, bisection, fixed-point) and returns `{rows, f, ...}`. `rows` is the full iteration history. On a page with a `method.js`, `result` only parses the committed inputs and calls the method from there.
3. `setup` — derives the data shared by the plots below from `result`: which rows are visible at the current step, axis ranges, and a sampled curve for the smooth function trace.
4. `mainPlot` — builds the primary Plotly chart. It's a closure over a `_plotDiv` variable so the same DOM node is reused across reactive re-renders (`Plotly.react` instead of `Plotly.newPlot` after the first render) — this is what preserves user zoom/pan when the step slider moves.
5. `iteratesPlot`, `convergencePlot` — Observable Plot charts covering the entire run (not just the current step), shown in an **open-by-default** "Convergence plots" callout (`::: {.callout-note collapse="false" title="Convergence plots"}`). They're diagnostic content worth seeing without an extra click, unlike the raw data dump below.
6. `iterationTable` — builds a DOM table via `VM.ui.renderTable`, shown in a **collapsed-by-default** "Iteration table" callout (`collapse="true"`) — raw per-row data, useful on demand but not something to lead with.

OJS cells wire Quarto `Inputs.*` controls (function text, initial guess/endpoints, max iterations) → `result` → an `Inputs.range` step slider → `setup` → `mainPlot(setup)`. OJS reactivity re-runs everything downstream when any input changes.

### Theme, design tokens, and site chrome

The site's look is **mathviz's optional Quarto theme**: `_quarto.yml`'s `format.html.theme.light`/`.dark` name `_extensions/apurvanakade/mathviz/theme/mathviz-light.scss`/`mathviz-dark.scss`, and this site has no theme file of its own. Those two files are *generated* by mathviz's `build.mjs` from mathviz's `src/theme/theme.scss`, a template the build fills in with the chrome tokens' values read out of mathviz's `src/css/tokens.css` — so `tokens.css` is the one place each color is written, and the Bootstrap chrome and the mathviz panels cannot disagree. Each generated file has two layers: `scss:defaults` sets the `$vm-*` tokens (`!default`) and Bootstrap's own `$variables` from them (`$body-bg`, `$link-color`, `$border-color`, `$font-family-sans-serif`, ...) so Quarto's built-in chrome (navbar, cards, callouts, tables) inherits the palette, and `scss:rules` re-emits the tokens as runtime `--vm-*` custom properties (`:root` for light, `body.quarto-dark` for dark) plus `--vm-font-sans` (Inter, so charts are typeset like the page) and `--vm-font-weight-display` (the thin titles), since JS has to read them at runtime (mathviz's `chart-theme.js` reads them via `getComputedStyle` to theme Plotly/Observable Plot charts — a Sass variable is compile-time-only and doesn't survive into the page). The chart palette (`--vm-color-*`) is not in the theme at all: `mathviz.css` declares it for every consumer. **To re-theme, change mathviz's `tokens.css`** (a pull request there, for every mathviz site), or — for this site alone — list a second SCSS file *after* mathviz's in `_quarto.yml` that sets a `$vm-*` token: the token wins and flows into both Bootstrap and `--vm-*`. Setting a Bootstrap variable directly there does *not* work: the theme assigns those without `!default`, because Quarto's own layer presets `$border-color`, `$border-radius` and `$card-cap-bg` as `!default` ahead of it and a `!default` in the theme silently lost (a diff of the compiled Bootstrap CSS caught all three at stock values). Page-local CSS names palette hues as `--vm-color-*` directly (the old `--vm-alt`/`--vm-accent2` aliases are gone). mathviz's CSS names no color except through `--vm-*` — never a raw hex, never a `--bs-*` fallback chain. (Two `rgba(0, 0, 0, …)` literals remain, for the report-bug popup's drop shadow and the share dialog's modal scrim; both are black-translucent in either theme, the same way `--vm-shadow`'s own value is, so neither is a palette color.) Fonts are Inter (body/UI) + JetBrains Mono (code), **self-hosted by the extension** (`mathviz: {fonts: true}` in `_quarto.yml`, off by default; the files and their `@font-face` blocks live in mathviz's `src/fonts/`, and the filter ships them as an html dependency, flat into `site_libs/quarto-contrib/mathviz-fonts-<version>/` beside `fonts.css`). They used to come from Google Fonts — don't put that back: a Google Fonts request hands Google every visitor's IP address before consent, which is the thing a German court ruled a GDPR violation, and `privacy.qmd` states that no font request goes to Google. The header comment in mathviz's `src/fonts/fonts.css` says how to refresh the files; mathviz's `src/fonts/fonts.test.js` guards the files and `scripts/fonts.test.js` guards this site's wiring.

The sidebar (`#quarto-sidebar`) is forced off-canvas at *every* width (not just Quarto's own sub-992px behavior) and driven by `.vm-sidebar-open`/`.vm-sidebar-pinned` classes on `<body>`, both by **mathviz's opt-in sidebar rail** (`mathviz: {sidebar-rail: vml-sidebar-pinned}` in `_quarto.yml` — the string is the pin's `localStorage` key, which `privacy.qmd` lists; `true` uses `vm-sidebar-pinned`; the source is mathviz's `src/chrome/sidebar-rail.{js,css}`, shipped as its own html dependency, which lands after Bootstrap's CSS, where the rules sat when they were this site's `styles.css`, so they win the same ties). It assumes a Quarto sidebar with `style: floating` and this site's `grid:` widths — Monte-Carlo-Methods uses the same. It is a small always-visible rail at the left edge (click the hamburger to open, click-to-pin, `Escape`/click-outside to close, pin state in `localStorage`) — deliberately **no** hover-to-preview: opening on pointer drift into the left edge churned `<body>`'s class list (see the `onThemeChange` guard in mathviz's `chart-theme.js`) and forced the rail's box to span the viewport, which left an invisible strip over the content column below 768px rather than Bootstrap's own `.collapse`/`.show` machinery, which this bypasses entirely. `#vm-sidebar-rail` is inserted at runtime, not server-rendered. mathviz's `sidebar-search: true` adds a title search box at the top of the sidebar; Quarto's full-text search stays in the navbar (one per page, and the sidebar is off-canvas).

### The mathviz library (installed in `_extensions/apurvanakade/mathviz/`)

Everything a second site could reuse — the `VM.<category>.<fn>` utilities (`expressions`, `numerical`, `sampling`, `filters`, `distributions`, `plotting`, `ui`, `discreteMath`, `mcmc`), the `ojs-*`/`vm-*` design-system CSS, the `--vm-*` token defaults, the optional theme and the opt-in chrome — is the **mathviz** library, authored in [apurvanakade/mathviz](https://github.com/apurvanakade/mathviz). This site is one of several consumers (Monte-Carlo-Methods is another), and it installs the library exactly the way the others do.

It used to be authored here and mirrored out. That stopped working once a second site contributed too: its changes had to detour through this repo's `develop`. mathviz is now the hub, and every site, this one included, sends library changes to it as pull requests.

- **Installing**: `scripts/update-mathviz.sh` (from mathviz's `kit/`) is `_quarto.yml`'s `pre-render` hook. Before every full render it installs the **latest tagged release** into `_extensions/apurvanakade/mathviz/` (`quarto add`/`quarto update extension`). In preview it checks at most once an hour; offline it keeps the committed copy. The installed copy is committed, so `publish.yml` has a working copy even without network. **Never edit it**: the next update overwrites it. A new mathviz release therefore reaches this site on its next render with no change here. Commit the updated folder in the same PR as whatever else is going out, and let `pr-check.yml`'s full crawl vet it. The release's `mathviz.lua` `VERSION` names `site_libs/quarto-contrib/mathviz-<version>/`, which is what busts returning visitors' caches, and bumping it is mathviz's job.
- **Wiring** is `filters: [mathviz]` and a `mathviz:` block in `_quarto.yml` — `referrer: same-origin`, `fonts: true`, and the opt-in chrome below — plus the two theme paths under `format.html.theme` (see the theme section above). The filter emits `<meta name="referrer">`, then the math.js and Plotly CDN tags, then `mathviz.js` and `mathviz.css`, all as html dependencies — which land in `<head>` *above* `include-in-header`. That is why the referrer meta is an extension option rather than a site include: emitted from the include, it would come after the CDN tags it exists to cover. `scripts/analytics.test.js` asserts the option is set and derives the third-party hosts `privacy.qmd` must name from the extension's Lua file; `scripts/verify-analytics.mjs` asserts the rendered order.
- **Changing a shared function or a design-system rule** is a pull request to mathviz, carrying its reference docs and CHANGELOG line (see that repo's CLAUDE.md). It reaches this site with the next release. To try it on a page here first, build mathviz and run `quarto add ../mathviz --no-prompt`. That installs the local build over the release, so restore the release (`QUARTO_PROJECT_RENDER_ALL=1 scripts/update-mathviz.sh`) before committing.
- **Needing a function before mathviz has it**, or one only this site will ever use: copy mathviz's `kit/` overlay in (`_mathviz/` + `_extensions/mathviz-local/`, listed after `mathviz` under `filters:`). It is laid out path for path like mathviz's `src/`, and `scripts/port.mjs` in mathviz moves files upstream from it. There is no overlay yet because nothing has needed one. A utility used by exactly one page stays with that page (see below).
- **Opt-in site chrome** (mathviz's `src/chrome/`, shipped in the extension's `chrome/`; each piece its own html dependency, added by `mathviz.lua` only when its option is set, with its settings passed as `<meta name="mathviz:...">` tags): `sidebar-rail: <localStorage key>`, `sidebar-search: true` (a title search atop the sidebar; stores nothing), `mobile-warning: <localStorage key>` (this site keeps its old `vml-` keys, which `privacy.qmd` lists), `split: <localStorage key>` (the split layout below; `vml-split-width`, also in `privacy.qmd`), `embed: true`, `share: {site-url, embed-docs}` and `report-bug: {repo, branch}` (branch defaults to `main`). `chrome/site.js` holds the helpers share and report-bug share (`VM.chrome.siteRelativePath`, which strips a subpath deploy such as a GitHub Pages project site); each script's pure builders are on `VM.chrome.<piece>`, tested next to it. Their stylesheets land after Bootstrap's CSS, where `styles.css` used to be, so they win the same cascade ties. The theme itself (`src/theme/theme.scss`) also carries the generic Quarto chrome rules: translucent navbar, footer, listing cards, quiet callouts, wide display math. Monte-Carlo-Methods uses the same options. What stays in this repo is what no other site would share: the analytics snippet, consent banner and giscus comments (`_includes/`), `privacy.qmd`, and a page's own colocated files. A utility used by exactly one page stays with that page (`apps/polynomial-interpolation/method.js`'s `cubicSpline`, or `apps/distribution-relationships/relationship-graph.js`, loaded by a page-level `include-in-header` that Quarto merges with the project-level one); propose something to mathviz only once a second *site* — not just a second page — needs it, or once it is generic enough that one plausibly would.
- **Page-level conventions that depend on the library** — the `vmTheme`/`chartColors` reactive pair, `showlegend: false` on every trace, `VM.plotting.emptyState` for an unparseable formula, `chartColors;` as a bare dependency line in cells that store a `VM.discreteMath.*Color` result — are described in the sections below and in the mathviz README; `apps/newton-method/index.qmd` is the reference wiring.

### Site structure: `apps/` and `topics/`

The whole site is exactly one level deep. There is no topic folder holding its own pages, no subtopic level, and nothing nested three deep:

- **`apps/<slug>/index.qmd`** — every interactive app and expository page, all siblings under one flat folder. A page's `topic:` front-matter field (e.g. `"Root Finding"`, `"Math Art"`) is what a topic listing page filters on — it must equal that topic page's `title:` exactly.
- **`topics/<topic>/index.qmd`** — one listing page per topic (Math Art, Sperner's Lemma, Probability, Root Finding, Interpolation & Integration, Differential Equations, Model Fitting), each a `listing:` over the glob `../../apps/*/index.qmd` filtered by `include: {topic: "<this page's title>"}`, `sort: "order"` (an app's `order:` front-matter field, not upload date). An app's `topic:` is therefore what places it, here and in the sidebar and the homepage's "Surprise me" button (below) -- there is nothing else to register. (This file used to say `listing.include` can't match a custom field like `topic:`; on Quarto 1.10 it does, checked on 2026-10-15 by a topic page that kept its own apps and dropped another topic's.) Each topic page also has an `order:` of its own: its position in the sidebar. There is no intermediate `computational-math/`, `discrete-math/`, or `data-science/` folder, and no subtopic folder — `probability/bayes/` and `probability/recursive-filters/` (two extra listing pages that existed only to group two apps each) were removed; Bayes' theorem and recursive filters are now just two `## `-level paragraphs inside `topics/probability/index.qmd`. Those broader areas (Computational Math, Discrete Math, Data Science) exist only as a `categories:` tag on each app page — there's no page or folder for the area itself.
- **The sidebar is generated**: `scripts/build-sidebar.mjs`, `_quarto.yml`'s second `pre-render` hook, writes `_sidebar.yml` (loaded through `metadata-files:`) with one section per topic page, in the topic pages' `order:`, holding that topic's apps in their `order:`. A sidebar glob can't do this, since `apps/*/index.qmd` can't be filtered by topic in a sidebar `contents:`, and the order is what drives `page-navigation` prev/next. **Don't edit `_sidebar.yml`**; change front matter. The script fails the render when an app's `topic:` names no topic page's `title:` (a typo would otherwise drop the page from every list silently), and rewrites the file only when it changes, since preview re-renders every page when a metadata file changes -- so adding a page, or changing a `topic:`/`order:`, costs one full re-render in preview. The file is committed so a single-page render has it; `scripts/registration.test.js` fails when the committed copy is stale.
- **The homepage's "Surprise me" button** (in the hero) links to a random app, re-picked on every visit. It used to be a "Random app" section embedding the app in a 900px `<iframe>`, removed as too heavy for the landing page. It reads its apps from a second, hidden listing on `index.qmd` (`id: random-apps`, the same `/apps/*/index.qmd` glob as the Gallery) whose template, `random-apps.ejs`, writes their slugs out as JSON -- not from the Gallery's DOM, which List.js paginates after load.
- **`apps/_metadata.yml`** gives every app `author: Apurva Nakade`; a page by someone else sets `author:` itself, which replaces the default rather than adding to it.
- `bread-crumbs: false` in `_quarto.yml`, deliberately: with one level of nesting there's nothing meaningful to trace, and Quarto gives an href-less sidebar `section:` the href of its first child — a plain-text grouping label used to render as a breadcrumb crumb that linked to the wrong page.
- `project.render: ["*.qmd", "**/*.qmd"]` in `_quarto.yml` is an explicit allowlist — without it Quarto also compiles the repo's own `CLAUDE.md`/`CONTRIBUTING.md`/`README.md` into published site pages.

### URL-shareable inputs and example presets

Most computational-math pages (e.g. `apps/newton-method/index.qmd`, `apps/numerical-integration/index.qmd`) make their state shareable via the URL's query string, and pair that with a "Try an example" dropdown near the top controls:

1. Each input cell reads its default value straight from `new URLSearchParams(window.location.search)` inline, falling back to a hardcoded default (e.g. `params.get("f") ?? "x^2"`) — so loading the page with `?f=...` pre-fills the field.
2. A `committed` cell — the one that actually feeds `result` — snapshots the current field values only when the Plot/Regenerate button fires (it reads the stable `viewof x` DOM views, not the reactive `x` values, so it does not rerun on every keystroke) and writes them back into the URL via `history.replaceState(null, "", ...)`, so the address bar is always a reproducible link to the current run. On pages with additional always-live controls that aren't gated behind a commit button (step counts, method checkboxes, etc. — see `apps/numerical-integration/index.qmd`), a separate `urlSyncControls` cell reactively keeps those in the URL too, alongside `initial<X>` helper cells that parse them back out on load.
3. An `examples` cell holds a single array `[{title, params}, ...]` of preset inputs. A `viewof exampleSelect` — `Inputs.select([null, ...examples], {label: "Try an example", format: e => e ? e.title : "Custom inputs", value: null})` — sits near the top controls. The dropdown always names the example the fields currently hold: a `syncExampleFromFields` cell reads every example field's value (so it re-runs when any changes) and calls `VM.ui.syncExampleSelect(viewof exampleSelect, examples, exampleFieldSelectors)`, which selects the matching example without dispatching an event. The leading `null` ("Custom inputs") shows only when no example matches — a shared link with its own inputs, or a field the reader edited — and is disabled and hidden in the list, so it can't be picked. There is no "Pick an example…" placeholder: it made the page's default state look like no example, when it usually is one. A page's defaults should therefore equal one of its examples, and that example goes first in `examples` (reorder rather than diverge): `npm run verify` fails a page that opens on any other example, as it does one that opens on "Custom inputs". An `applyExampleFromSelect` cell attaches a **one-time native `"change"` listener** to `(viewof exampleSelect).querySelector("select")` (not an OJS cell reactive on `exampleSelect`'s value — see the gotcha below) that reads `(viewof exampleSelect).value` and calls `VM.ui.applyExampleParams(exampleFieldSelectors, example.params, viewof plotTrigger)`, which sets each field's view and clicks Plot/Regenerate in place — no page navigation, so no reload and no scroll jump. There is no bottom example gallery/grid — the dropdown is the way to load presets. Prose may still link to one example by its query string (e.g. `apps/particle-filter-tracking/index.qmd`'s "Example 1"); such a link reloads the page with that example's inputs, so its query string must match the example's `params` exactly — update both together. See mathviz's `src/js/ui/apply-example.js`.

**Every input on the page must be wired into the URL whenever possible** — not just the function/endpoint fields gated behind the commit button. Step counts, method checkboxes, and any other always-live control need both an `initial<X>` cell reading it back out (step 1) and an entry in `committed`/`urlSyncControls` writing it back (step 2), the same as `apps/numerical-integration/index.qmd`'s `initialN`/`initialMax`/`initialMethods` + `urlSyncControls`. For a checkbox group, add a slug↔label `Map` pair (`methodSlugToLabel`/`methodLabelToSlug`) so the URL uses short stable slugs instead of the human-readable labels verbatim. An example's `params` object is a contract: every key it sets must actually appear in `exampleFieldSelectors`, or the example silently doesn't do what it claims — worth checking on any edit. (`apps/explicit-ode-methods/index.qmd` shipped for a while with `n`/`max`/`show` params on every example that no cell ever read, back when examples were a hand-written `<div class="example-grid">` of `<a href="?...">` links — that pattern is retired; don't reintroduce it.)

Two non-obvious gotchas in this wiring, both found the hard way (see mathviz's `src/js/ui/apply-example.js`'s comments for the full explanation):

- `exampleFieldSelectors` values are `data-example-field` CSS selectors (plain strings tagged onto each `viewof` cell's returned element), not direct `viewof` references. When a field's bounds reactively depend on another field (e.g. a step slider capped by a "max" field), OJS recreates that field's `viewof` cell whenever the upstream field changes. A cell that references such a view by name becomes reactive on it — and since applying an example is what changes the upstream field, a direct-reference version re-triggers itself in an unbounded loop (a real one was caught here: writing "max" recreated the "n" slider's view, re-triggering the apply cell, which wrote "max" again — until Chrome's history-API throttling kicked in). List an upstream field (e.g. "max") before any field that depends on it (e.g. "n") in `params` — `applyExampleParams` applies params in object order with a 100ms yield between each (measured: OJS's own reactive updates settle in ~40ms, not one tick), giving a recreated view time to exist before the dependent field is applied.
- The dropdown's trigger must be a plain DOM event listener attached once (the `enterToPlot` pattern), never an OJS cell reactive on `exampleSelect`'s value — a native `<select>` fires both `input` and `change` per selection, so a reactive cell runs twice, and the two overlapping calls race (this corrupted a field's final value in practice).

### Split layout: the app beside the text

App-first pages show the app in a pane on the right, fixed under the navbar and down to the bottom of the window, while the prose scrolls in a column on the left. It is mathviz's opt-in `split` chrome (`mathviz: {split: vml-split-width}` in `_quarto.yml`; `chrome/split.{css,js}` there, documented in mathviz's `docs/site.qmd#split`), and a page opts in by wrapping everything after its copyright comment in `::::::::: {.vm-split}` … `:::::::::`, around its `<div class="vm-app">`. Nothing else is per-page: no include, no front matter.

- **Which pages.** Every app page except the three Sperner's Lemma pages (articles with several figures, which read as one column), `apps/positive-predictive-value/index.qmd` (also an article: prose, then the app, then more `##` sections; split briefly, reverted by the owner's call), and `apps/distribution-relationships/index.qmd` (looked wrong split, by the owner's call). The pane holds only a `.vm-app` that is a *direct* child of `.vm-split`; a second app wrapped in a plain `<div>` stays in the text column, after the prose that introduces it (`apps/polynomial-interpolation/index.qmd`'s `#basis`). A chart there is under 600px wide, where mathviz hides a floating legend (as on a phone), so give it none: that page's basis chart follows the main chart's legend. A new method page gets it from `apps/_template/index.qmd`. An expository page decides per page; ask.
- **What it does.** From 992px up the pane is about half the window and the title, prose, page navigation and footer share the rest; its charts (`.plotly-box-large`) share whatever height the controls leave, and an app with no Plotly chart is centered in it. The divider drags, moves with the arrow keys and is remembered under `vml-split-width` (double-click resets it). Below 992px the page is one column, app first, and `?embed=` shows the app alone exactly as on any other page.
- **No TOC on a split page.** `toc: true` adds a right-hand rail that breaks the split layout; an essay page that wants a TOC stays one column (see Conventions).
- **Sliders go above their chart, never below it.** In a pane fitted to the window a control under the chart is the first thing pushed out of view, which is how this rule was found (`apps/polynomial-interpolation/index.qmd`'s k slider, the first time it was split).
- **Prose doesn't say where the app is.** "The app below", "the chart above" are wrong on a split page, where the app is beside the text, and wrong again on a phone. Say "the app", "the chart", "in the example shown".
- **Prose comes before the callouts.** On a split page the left column is what a reader reads beside the app, so the explanation goes right after the `vm-app` block, then the "Convergence plots"/table callouts, then (if any) `## References`.
- **Locked-axis charts need nothing.** A chart with `scaleanchor` (`apps/spirographs/index.qmd`, `apps/particle-filter-tracking/index.qmd`) used to zoom further out on every resize, which the divider made constant. mathviz's Plotly patch and `VM.plotting.autoResize` now keep the reader's view (`VM.plotting.trackView`/`fitView`), so such a page just passes its ranges and a `uirevision`; don't reintroduce the per-page `firstFit` observers or range copying.
- **Tall controls overflow.** A pane too short for its controls scrolls; at 1280×720 recursive-filters does by 65px, and particle-filter does by 168px with the pane dragged to its 480px minimum. All of it is before the first scroll, which slides the navbar away and gives the pane 66px more. A one-row slider bar was tried for recursive-filters and rejected: the 94px number boxes left 0–93px tracks.

### Chart controls: floating legend, attached slider bar

Every control that's *always-live* (reacts immediately, no Plot/Regenerate button gating it) and whose only job is to change what the chart currently shows — a trace-visibility legend, a step/iteration scrubber, a model parameter like `n` or a filter's α/R/Q — belongs with the chart rather than in the controls panel further down the page. This is a uniform layout convention, not a per-page style choice: it's what's left every single `panel-tabset` on the site collapsing (see below), since in every case the second tab turned out to be exactly this category of control.

**The two live in the chart's wrapper but not in the same way, and the difference is the point.** The legend genuinely floats over the plot: it's small, it hugs a corner, and it's draggable, so the reader can move the one thing it covers. The slider bar does **not** float — it sits in normal flow directly *above* the chart, inside the same wrapper. It used to be pinned over the chart's bottom edge like the legend, and that was a mistake: a full-width bar parked across the bottom of a plot covers exactly the region a reader scrubbing a step slider is watching, and it covers it *permanently*, on every page, for every reader. Translucency, a collapse button and drag-to-move were all considered and rejected as ways to paper over that — each one asks the reader to keep managing a problem the layout created. Reserving the space instead means the chart is never obscured at all, and costs only the bar's own height, which `.plotly-box-large`'s 72vh (down from 78vh) gives back.

**Above the chart rather than below it**, because every other control on the page — the whole `.ojs-panel` — is above it, so a bar underneath left the reader's eye travelling past the chart and back again to find it. Reading order is now panel, sliders, chart. That order is set with flexbox `order` on `.ojs-chart-block` rather than by moving the div in all 14 pages' markup, which also keeps the bar inside the wrapper, where fullscreen needs it. One consequence worth knowing: the legend is absolutely positioned, and its containing block used to be `.ojs-chart-block`, whose top edge *was* the chart's top edge — with the bar above, it no longer is, and the legend would sit on the sliders. The legend's own (zero-height) cell is therefore ordered between the bar and the chart and made the containing block, which puts the legend back at the chart's top-left corner with no JS and nothing to keep in sync with the bar's height. That in turn requires switching off `.cell-output-display`'s `overflow: auto` for that one cell, or the wrapper clips the legend to a zero-height box, i.e. to nothing — the same trap mathviz's `slider-play.js` popover hit, solved there with the top layer.

1. Wrap the page's `mainPlot` cell in `<div class="ojs-chart-block">` (`position: relative` in mathviz's `chart-block.css`, the positioning anchor for the legend). Fullscreening a chart via the shared modebar button (mathviz's `plotly-fullscreen-button.js`) fullscreens this wrapper rather than the bare Plotly div when present, so everything inside it — legend and sliders alike — stays visible in fullscreen. **That is also why the slider bar goes inside this wrapper even though it no longer floats**: a bar that were merely a sibling of the wrapper would vanish the moment a reader fullscreened the chart. In fullscreen the wrapper becomes a flex column so the chart takes the height the bar leaves; the chart's letterboxing measures itself against that remaining box via container-query units (`100cqh`/`100cqw`), not `100vh`/`100vw`, which would overstate the available height by the bar's own and stretch the chart wider than its on-page aspect ratio.
   - **A page that draws its own SVG (Observable Plot, or a hand-built `<svg>`) instead of a Plotly chart gets no modebar, so it gets no fullscreen button from that patch.** Add `ojs-svg-block` next to `ojs-chart-block` on the wrapper (`<div class="ojs-chart-block ojs-svg-block">`, holding the `.ojs-chart-controls` bar and the drawing cell) and mathviz's `svg-fullscreen-button.js` does the rest — see its entry in the mathviz CLAUDE.md. Nothing else is page-specific: no button cell, no page-local CSS, no aspect ratio to record. Every Sperner's Lemma app and `apps/positive-predictive-value/index.qmd` are wired this way; `apps/sperners-lemma-geometric-proof/index.qmd` is the one with a wrinkle worth knowing (two captioned plots side by side in one cell — its page-local `<style>` keeps that pair a row in fullscreen, spelled with both block classes because the shared chain rule ends in `:has()`, which counts its argument's specificity). The opt-in is a class rather than auto-detection ("any block without a Plotly chart") because OJS renders cells asynchronously — at load time a Plotly page's block has no chart in it yet either. A page-level floating element appended to `<body>` (the PPV page's hover tooltip) must be reparented into `document.fullscreenElement` while fullscreen is active: the Fullscreen API paints only the fullscreened subtree on top, and a body child sits *under* it whatever its z-index.
2. A trace-visibility legend (`viewof <name> = VM.ui.legendOverlay(...)`, mathviz's `legend-overlay.js`) is a direct sibling of the `mainPlot` cell inside that wrapper, floating top-left via `.ojs-legend-overlay`. **This replaces Plotly's built-in legend, it doesn't sit alongside it** — every trace `mainPlot` pushes carries `showlegend: false`, so Plotly draws no legend of its own (with two or more traces it otherwise auto-shows one, in Plotly's default style, in the top-right corner — visibly not this site's chrome). The wiring, copied verbatim across pages (`apps/newton-method/index.qmd` is the reference): a `traceOptions` cell listing the labels in display order, a `traceColors` `Map` from label → the exact color `mainPlot` draws that trace in (so the swatches double as a color key), one `show<Trace> = traces.includes("<label>")` `//| output: false` cell per trace, and `mainPlot(setup, ...show<Trace>)` gating each `data.push` on its flag — a hidden trace is never pushed, rather than pushed with `visible: false`.
   - **When the trace set is decided at runtime** (a page where selecting something changes *which* distributions/series are drawn, e.g. `apps/distribution-relationships/index.qmd`), the fixed wiring above doesn't apply: there is no static `traceOptions` list and no way to write one `show<Trace>` cell per trace. Derive the `[{label, color}]` array in a cell instead and pass it straight to `legendOverlay`, then have the plot cell skip any series whose label isn't in the view's value — same contract (`showlegend: false` on every trace, a hidden trace never pushed), just computed. Two things to get right: keep the labels **stable** (a label carrying a parameter value rebuilds the legend on every slider move, which flickers and silently discards whatever the reader had toggled off — put the values in the trace's Plotly `name`, which only shows on hover), and hide the panel when it has no rows via `:not(:has(.ojs-legend-item))` rather than `:empty`, since `draggable-overlay.js` appends its grip as a child and `:empty` therefore never matches.
   - A page whose *controls* are likewise dynamic has to build them in one cell, which puts Quarto's own output wrappers between `.ojs-chart-controls`'s grid and the sliders, so the grid sees one child and stacks them in a column. Make that cell's own container the grid (`display: grid` with the same `auto-fit` track) rather than collapsing the wrappers with `display: contents` — the wrapper class names (`.cell-output-display`, `.ojs-in-a-box-waiting-for-module-import`) are generated markup no page should depend on. Keep `.ojs-grid` on the controls div so mathviz's label-above-track rule (`panel.css`), which matches forms at any depth, still applies.
3. Every always-live slider is a further sibling, wrapped in `<div class="ojs-chart-controls">` (mathviz's `legend-controls.css`) — a normal-flow block directly above the chart, spanning its width, wearing `.ojs-panel`'s solid `--vm-surface` chrome rather than the legend's blurred translucent card (there's no curve behind it to show through any more). **The bar holds sliders and nothing else** — with one deliberate exception: a small always-live control whose only job is to change what the chart currently shows (the PPV page's Shuffled/Sorted radio, the Sperner apps' "Regenerate colors" button) may sit at the bar's right end as the `.ojs-row`'s last div, since a controls panel holding nothing but that one button would be silly; a *text field* never does. A text field that bounds one (every page's "Max"/"Max steps"/"Max depth") used to share the bar with its slider; it lives in the controls panel now, sharing the one `.ojs-grid` row with the commit-gated fields, still always-live. Keeping the two apart is what leaves room for the play button (mathviz's `slider-play.js`, which enhances every slider automatically — no per-page wiring, no speed field) that sits inline at the left of a track, and the same separation holds in a panel: no `.ojs-row`/`.ojs-grid` group anywhere mixes a range slider with a text box. A bar with two or more sliders (e.g. `apps/recursive-filters-1d/index.qmd`'s four filter parameters) additionally stacks each one's label above its track — the same layout `.ojs-panel` already uses — via a rule scoped to `.ojs-chart-controls.ojs-grid`, since the auto-fit grid track otherwise leaves too little width for label, track, readout, and the play button side by side.
   - A single slider: no layout primitive at all (`<div class="ojs-chart-controls">`), since there is nothing to lay out against.
   - Three or more controls (e.g. `apps/recursive-filters-1d/index.qmd`'s four filter-parameter sliders): combine with `.ojs-grid` instead (`<div class="ojs-chart-controls ojs-grid">`), which auto-wraps into multiple rows on narrow viewports rather than cramming everything into one line.
   - Any `//| output: false` helper cell these sliders depend on (a `maxN`/`tolerance`/`maxSteps` parser) is declared just above `.ojs-chart-block` opens, not inside the row/grid div — an output:false cell placed inside an `.ojs-row`/`.ojs-grid` still emits a real (zero-size) `.cell` node that counts as a flex/grid child and steals the first-child/last-child (or column) layout meant for a visible sibling.
4. `data-example-field` tagging still works with a field in the controls bar exactly as it does for a field in the panel — `document.querySelector` finds it in the DOM regardless of where it sits (see the example-dropdown wiring below).
5. **The legend is draggable, for free.** mathviz's `ui/draggable-overlay.js` finds every `.ojs-legend-overlay` inside an `.ojs-chart-block` and gives it a grip (revealed on hover at the panel's right edge) that moves it off whatever part of the curve it's covering, clamped to the chart, remembered per page in `localStorage`, double-click or `Home` to reset. A new page needs no wiring: don't call anything, and don't hand-position the legend to dodge a curve. **The slider bar is deliberately not in that selector** — it covers nothing, so there is nowhere to drag it to, and leaving it out is also what stops an offset stored back when it *did* float from shoving the in-flow bar out of place (this module is the only thing that ever writes `transform` on these panels, so a bar it never touches simply renders where the stylesheet puts it, and the stale entry is inert rather than actively wrong). Two things to preserve if you touch this: the grip is `position: absolute` so it takes no `.ojs-grid` track, and mathviz's `.ojs-row > div:first-of-type`/`:last-of-type` sizing (`panel.css`) must stay `-of-type` — as `:first-child`/`:last-child` (which it was) *any* inserted non-div sibling stops it matching at all, since that reads "a div that is also the first child", not "the first div". This is the same trap as the `output: false` note in 3 above, one step further along.

6. **Moving a slider must never rescale the chart's axes** — the ranges come from something the slider can't change. *Which* fixed scale a slider gets is the page owner's decision: when adding or changing an always-live slider, ask them rather than picking one.

**A page's remaining controls panel holds only what's left**: text fields gated behind a commit button (function, endpoints, initial conditions), the always-live "Max"/"Max steps"/"Max depth" field that bounds the chart's slider, the example dropdown, the Plot/Regenerate button, and any button-triggered action (e.g. `apps/l1-vs-l2-regression/index.qmd`'s "Regenerate points").

**Two rows, not one row per field.** Row one is a `.ojs-row` holding exactly two cells: the formula field and the Plot button. Row two is a `.ojs-grid` holding *everything else* — the scalar fields, the Max field and the example dropdown — auto-fitted into columns. That is the whole panel, 124px of it; see `apps/newton-method/index.qmd` for the reference wiring. It replaces a layout that gave each field its own full-width block row and left the Plot button alone on a line of its own, which measured 322px to hold about 150px of controls.

Pairing the formula with Plot is what makes row one work. `.ojs-row`'s own rules do the arranging — `:first-of-type { flex: 1 1 200px }` grows the formula's cell, `:last-of-type { flex: 0 0 auto }` keeps the button at its natural size — so the button lands flush against the panel's right edge and the two bottom-align. The one rule this needs is in mathviz's `panel.css`: an expression field inside a `.ojs-row` drops its 20em default and takes `width: 100%`, i.e. whatever the button leaves. Without that the field would sit at 20em with several hundred pixels of dead panel between it and the button — the exact emptiness the two-row layout exists to remove. The `resize: horizontal` affordance survives; it just starts from the full width.

Three things the old layout depended on are gone and shouldn't come back: the Max field no longer sits in a separate `.ojs-grid` group below the others (it used to, so the panel would read *what to compute*, then *how far the sweep runs* — but it is now URL-wired and example-settable like every other input, so it is no longer a special case); the Plot button no longer carries `.ojs-end` (that class right-aligns a lone button under a grid, and `.ojs-row`'s `:last-of-type` rule now does the same job); and no field gets a block row to itself. Every `//| output: false` cell — `exampleFieldSelectors`, `applyExampleFromSelect` — sits *outside* both the row and the grid, since a hidden cell still emits a real zero-size `.cell` node that would take a track and, in the row, would break the `:first-of-type`/`:last-of-type` sizing outright. (There is no separate "Play step"/speed field anymore — mathviz's `slider-play.js` derives playback speed from the slider's own range, and the reader picks a multiplier from the popover on the play button itself.)

### Tabbed controls: don't

`::: {.panel-tabset}` is not used anywhere on the site, and reaching for it is almost always a sign of the mistake it used to encode. Every tabset this site ever had (`apps/explicit-ode-methods/index.qmd`'s "Inputs"/"Display Options", `apps/recursive-filters-1d/index.qmd`'s "Signal & Sampling"/"Filter Parameters", every Root Finding app) turned out to be exactly "panel fields" vs. "sliders that belong with the chart", and collapsed into a single `ojs-panel` once those sliders moved into the chart-controls bar. **Before splitting controls into tabs, check whether the second group is just sliders or legend toggles that belong with the chart** — it has been, every time so far; use the pattern above instead.

A page whose controls are genuinely one group stays one plain `ojs-panel`; don't force a single-tab tabset for consistency's sake. If a page ever does turn out to need real tabs, they should be wired to a `tab` URL query param like every other input on the site — `git log -S panel-tabset` has the worked implementation that was removed, including why it matched tabs by visible label text rather than by Quarto's auto-generated `tabset-1-1` IDs.

### Adding a new method page (Root Finding, Interpolation & Integration, Differential Equations, or any other computational-math topic)

1. Create `apps/<slug>/index.qmd` — `cp -r apps/_template apps/<slug>` (a working fixed-point-iteration starter with every shared cell and a `TODO` at each thing to change; Quarto ignores the underscore-prefixed original, so it is never rendered or listed) or copy a finished page (e.g. `apps/newton-method/index.qmd`), and adapt its `method.js` (examples, method, convergence fit), its `method.test.js` (what each example's convergence plot should report, and why) and its `result`, `setup`, `mainPlot`, `iteratesPlot`, `convergencePlot`, and `iterationTable` cells to the new method's math and input fields; `npm test` runs the new page's examples. All `VM.*` utilities, the design-system CSS and the CDN scripts are already on every page via the mathviz extension — no per-page script block needed. Keep the `<div class="vm-app">` wrapper around the controls panel and chart block (see the Embed mode section) — it's what `?embed=1` shows. Keep the `::::::::: {.vm-split}` wrapper around the page too (see the Split layout section), unless the owner wants the page as one column. Give it `topic: "<Topic Name>"` matching an existing topic page's `title:` exactly (or a new one, see step 3), a `categories:` list from the fixed vocabulary (see Conventions below) including `Computational Math` as one entry, and a short `description:` in plain text -- an imperative phrase ending in a period, like `"Find a root by following tangent lines down to the x-axis."` (no math markup — it's excerpted verbatim onto the page's listing card; without one, Quarto falls back to the page's first prose paragraph, which on these pages is the trailing explanation, not a summary). Pick categories only from the vocabulary in Conventions below; they drive the homepage Gallery's category cloud.
2. Give the front matter an `order: <n>` field one higher than the current last app in that topic. That and `topic:` are all the registration a page needs: its topic page's listing, the generated sidebar (which also drives `page-navigation` prev/next) and the homepage's Gallery and "Surprise me" button all find it from its front matter (see the site-structure section above).

User-entered expressions are evaluated in-browser. Use `VM.expressions.makeFunction`/`VM.expressions.makeDerivative` (they handle normalization and error catching, returning `null` on a bad expression) rather than calling math.js directly. Currently, invalid input just makes `result` return empty `rows` (blank chart, empty table) — there's no surfaced error message to the user yet.

### Adding a new expository/proof page (Sperner's Lemma, or any future non-computational-math topic)

An expository page lives in `apps/` exactly like an interactive one — there is no separate folder for prose pages — and takes the same steps as above with one addition:

1. Create `apps/<slug>/index.qmd`. Give it `topic:` matching an existing (or new) topic page's `title:`, a `categories:` list from the fixed vocabulary (see Conventions below) including the area tag (e.g. `Discrete Math`) as one entry, and a short imperative `description:` (see the computational-math section above — same reason, same convention). Pick categories only from the vocabulary in Conventions below.
2. Give the front matter an `order: <n>` field (reading order within the topic; these pages are proof/exposition steps, not independent methods, so order matters more than for computational-math topics).
3. If this is a brand-new topic (not just a new page under an existing one), also create `topics/<topic>/index.qmd` — copy `topics/math-art/index.qmd`'s front matter, set its `include: {topic: ...}` to the new page's `title:` and its `order:` to where it goes in the sidebar (renumbering the topics after it), and add a homepage tile in `index.qmd`'s "Browse by topic" section. The sidebar section follows from the page itself. There is no separate "broad area" page or folder — Computational Math / Discrete Math / Data Science / Probability exist only as `categories:` tags on the app pages themselves.
4. Not every page needs interactivity — `apps/barycentric-coordinates/index.qmd` and the proof pages mix substantial static exposition with one or two `{ojs}` apps, unlike computational-math pages which are interactive-app-first with prose secondary. Whatever the mix, wrap each interactive figure in a top-level `<div class="vm-app">` (with an `id` when there is more than one) so `?embed=1`/`?embed=<id>` can show it alone — see the Embed mode section.

## Math exposition conventions

Patterns established across the Sperner's Lemma proof pages, worth reusing for future proof/exposition content rather than reinventing per page:

- **Crossref-labeled theorem/definition callouts**: `::: {#thm-name}\n...\n:::` (also `#def-`, `#cnj-` for conjectures/claims still to prove, `#cor-` for corollaries), referenced elsewhere in the same or other pages via `@thm-name` — Quarto resolves these to numbered links ("Theorem 1") automatically. Pick a short, descriptive slug (`#thm-sperner-local`, not `#thm-1`) since it's also the anchor.
- **Scaffolded exercises**: a `::: {.callout-tip title="Exercise"}` with the claim to prove (referencing it via `@cnj-name` rather than restating it) and numbered sub-steps, followed by one or more `::: {.callout-note collapse="true" title="Hint for step N"}` / `title="Solution sketch"` callouts a reader has to click to reveal. See `apps/sperners-lemma-combinatorial-proof/index.qmd`'s proof of `@cnj-bottom` for the full pattern. Don't put a crossref inside a callout's `title="..."` attribute itself (e.g. `title="Exercise: prove @cnj-bottom"`) — Quarto doesn't resolve crossrefs inside raw attribute strings, only in rendered body content, so it leaks through unprocessed; put the crossref in the callout body instead.
- **Color words in prose**: when a sentence names a color the diagram draws ("the red vertex", "RGB triangles"), tint the word with `<span class="vm-swatch vm-swatch-alt">red</span>` (mathviz's `swatch.css`; one modifier per palette token — `-fn`/`-alt`/`-ok`/`-muted`/`-ink`/`-warn`/`-accent2`/`-accent3` — named for the token so the swatch is the same hue as the dot or fill it describes, in both themes; `-accent` is the UI accent, not a chart color, so a blue *vertex* is `-fn`, the token `vertexColor('blue')` reads). Never an inline `style="background-color:red"` — a CSS named color is not the site's red and stays put when the theme flips. A page needing a shade the modifiers don't cover (the geometric proof's light/dark orientation hatches) defines its own class in its page-local `<style>` on top of `.vm-swatch`, still in `--vm-*` terms.
- **Plot figures are diagrams, not graphs**: a triangulation gets `axis: null` on both scales and `grid: false` (through `VM.plotting.plotOptions`, which otherwise turns the grid on), and a height computed from the width so a unit-wide equilateral triangle is drawn to scale — Plot stretches `y` to whatever height it is given. Strokes are `chartColors.ink`, a hollow marker's fill is `chartColors.halo`, never `"black"`/`"white"`.
- **References**: a `## References` section near the end, plain Markdown citations with inline links (author, title, venue, year, URL) — see `apps/sperners-lemma-geometric-proof/index.qmd` for the existing example. No BibTeX/CSL setup in this project yet. **Cite only sources the app itself directly rests on** — the paper that introduced the method or result the page computes or proves, or the source of a specific variant it implements — never general background reading on the broader topic (a textbook, survey or Wikipedia article that isn't the source of something the app does). A page is an app, not an article. Give each entry the citation and its link only, with no annotation after it explaining why it is cited.
- Interactive apps embedded in an expository page follow the same shared-palette conventions as any other page (`VM.discreteMath.*` for triangle/edge coloring, etc.) — exposition pages aren't exempt from the shared-library rule just because they're prose-heavy.

## Conventions

- TOC is **off** site-wide (`toc: false` in `_quarto.yml`): most app pages have no `##` headings at all (the app is the page), and listing pages have none either, so the default TOC was an empty rail. A page with real `##` sections may opt in with `toc: true` — `privacy.qmd` and the one-column essay pages (`cats-on-ladders`, `positive-predictive-value`, `sperners-lemma-geometric-proof`, `sperners-lemma-combinatorial-proof`) do; a page with one section (`sperners-lemma-statement`) doesn't, since a one-entry rail is noise. **A split-layout page (`.vm-split`, see the Split layout section) never gets a TOC**: the rail breaks the layout. Don't add `toc: false` anywhere; it's already the default.
- **Categories are a fixed vocabulary, shown as a cloud above the homepage Gallery's cards** (`categories: cloud` on `index.qmd`'s `latest-listing`; clicking a word filters the Gallery in place via `#category=`). `_includes/category-cloud.html` (styles and script, included by `index.qmd`'s front matter) moves the cloud out of the right margin, too narrow on this layout and hidden on a phone, into a row above the cards, with Quarto's "Categories" reset title relabelled "All". Topic pages have no cloud: with two to six apps, Quarto sized their few tags at up to 2.5x body text. The vocabulary is: areas `Computational Math`, `Discrete Math`, `Data Science`, `Probability`; kinds of page `Math Art`, `Visual Proof`; ideas `Convergence`, `Error Analysis`, `Integration`, `Interpolation`, `Regression`, `Filtering`, `Bayes' Theorem`, `Geometry`, `Parametric Curves`, `Combinatorics`. Every page takes its area (or `Math Art`) plus whichever ideas it is genuinely about. Don't invent a tag for one page: categories were rendered once before and retired when 53 one-off strings across 20 pages made the rail useless; a new tag needs at least two pages, and a topic name (Root Finding, Differential Equations, ...) is not a tag, since the "Browse by topic" tiles already cover it. (`Math Art` and `Probability` are the deliberate exceptions: a kind of page and an area that happen to share a topic's name.) Specific terms (a method's name, a convergence order) belong in `description:` and the prose. Tags also show on every listing card (`categories` in its `fields:`) and under each page's title (Quarto's default `title-block-categories`). **Every tag outside the homepage opens the homepage Gallery filtered to it**: `_includes/category-links.html` (site-wide) catches the click, since Quarto would otherwise filter a topic page's own cards, or link a title's tags to whichever listing the reader came from (it checks `document.referrer`), and a topic page has nothing to clear that filter with (reload and Back keep it, re-applied from the hash). On the homepage a card's tag filters the Gallery in place, and `index.qmd` scrolls to the Gallery when it opens with a `#category=` hash.
- Every new code/content file must begin with the copyright/license header for its file type — see `CONTRIBUTING.md`. Authorship is per-file and per-contributor; add your name to `Authors:` for significant additions.
- **CSS used by exactly one page stays with that page.** There is no site-wide stylesheet: the `ojs-*`/`vm-*` design-system primitives are mathviz's `src/css/**`, the site chrome is mathviz's theme and `src/chrome/`. A rule that targets markup only one page emits (a bespoke SVG diagram, a one-off widget) belongs in a `<style>` block in that page's own `.qmd`, or a `.css` file in the same folder, the same way `apps/distribution-relationships/relationship-graph.js` is colocated rather than promoted into mathviz. `apps/distribution-relationships/index.qmd` is the reference: its whole `.ojs-graph-*` block lives in the page. Deleting a page deletes its styles with it instead of leaving orphaned rules nobody dares remove. Promote a block into mathviz (`src/css/` for design system, `src/theme/` or `src/chrome/` for chrome) only once a second page actually needs it. Page-local CSS is **not** exempt from the token rule below — it consumes the same `--vm-*` custom properties, so a colocated block still re-themes with the site.
- Interactive pages reuse mathviz's design-system CSS classes (`ojs-panel`, `ojs-row`, `ojs-grid`, `ojs-fill`, `ojs-auto`, `ojs-table-container`, `ojs-table-toolbar`, `plotly-box-large`) rather than ad hoc per-page styling. `ojs-panel` is chrome only; `ojs-row`/`ojs-grid` are layout only — combine them (`class="ojs-panel ojs-row"`) for a standalone panel, or nest a bare `ojs-row`/`ojs-grid` inside an `ojs-panel` for a control group within a larger panel. Attach `ojs-fill`/`ojs-auto` via `classList.add` on an `Inputs.*` wrapper div to make it fill its row or keep its natural width, instead of setting `el.style` directly.
- **Observable Inputs injects its own `.oi-<hash>` rules into `<head>` at runtime**, i.e. *after* every stylesheet in the cascade (mathviz's included). Any rule of this project's that targets one of those generated forms and ties on specificity therefore **loses**, silently and only in the browser. A bare single-class selector (`.vm-has-play { flex-wrap: wrap }`) is exactly such a tie — it computed to `nowrap` and squeezed slider tracks to 0px. When styling an Observable-generated form, either out-specify it (add the scoping `.ojs-panel`/`.ojs-chart-controls` class plus `form[class^="oi-"]`, as every rule in that part of the file does) or use `!important` (the established idiom here — see the `flex: none !important` on the number spinner). Don't assume a class you invented is safe just because nothing else in `styles.css` defines it.
- **`npm run verify` does not assert layout.** Until 2026-10-15 it also measured every slider's track width, opened every playback popover, checked sliders sat above their chart, re-loaded each page at a phone's 390×844 and again with `?embed=`, and inspected the Share dialog. It was cut back to one load per page because those checks mostly tested mathviz's CSS and chrome rather than the pages, tripled the crawl's time and were flaky on a busy CI runner (particle-filter failed on runs that were then re-run green). A layout regression from a mathviz release — a slider squeezed to 0px by Observable Inputs' runtime `.oi-<hash>` rules, a popover clipped by an `overflow` wrapper — no longer fails CI, and neither does a page that scrolls sideways on a phone (the spirographs equation table and distribution-relationships URLs once did): mathviz has no browser tests, so nothing checks layout. Look at a changed page yourself, at a phone's width (390px) too, and at a page that uses a changed mathviz function. `git log -S checkSliderControls` has the removed checks and their measured thresholds if one is ever wanted back, in mathviz's tests or here.
- Observable Inputs renders every control as `<form class="oi-...">` with its label and control as flex-row siblings; mathviz's `panel.css` overrides this to stack the label above the control instead (`.ojs-panel form[class^="oi-"] { flex-direction: column; ... }`), so that when a label wraps to more lines than its neighbor's (a narrow `.ojs-grid` column, a long parameter name), the control still bottom-aligns consistently across a shared `.ojs-row`/`.ojs-grid` — with label-beside-control, a taller-wrapped neighbor left the shorter field's control vertically off from the others. `.ojs-panel input[type="text"]`'s default width (10em) is sized for the short scalar values most fields hold (an endpoint, a seed, a max-iteration count); a field that genuinely needs to hold a long formula (`fText`, `gText`, `y' = f(t, y)`) opts into `.ojs-fill` instead of relying on a wide default — every existing formula field already does this, so don't widen the default itself to accommodate one.
- Keep each page's logic in small named OJS cells (`result`, `setup`, `mainPlot`, `iteratesPlot`, `convergencePlot`, `iterationTable`) rather than one large cell, and keep the same cell names/shapes across method pages for consistency.
