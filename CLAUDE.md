# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Visual Math Lab is a Quarto website of interactive, browser-based visualizations of numerical methods. There is no backend and no build tooling beyond Quarto — all interactivity runs client-side via Observable JS (OJS) cells in each page, math.js and Plotly from CDNs, and the **mathviz** library ([apurvanakade/mathviz](https://github.com/apurvanakade/mathviz)): the shared `window.VM` utilities, the `ojs-*` design-system CSS and the `--vm-*` token defaults, vendored here as a Quarto extension under `_extensions/`. **This repo is content**: app pages, topic listings, the site theme and chrome. Anything a second site could reuse lives in mathviz, not here.

## Commands

- `quarto render` — render the whole site into `docs/` (`_quarto.yml` sets `project.output-dir: docs`).
- `quarto render apps/newton-method/index.qmd` — re-renders that page plus any listing/index pages that glob-discover it (its topic index, the homepage) — lighter than a full-site render, but **not** a true single-page render (it's still a multi-file batch job, not something you can point a browser at). For actually isolating one page, use `quarto preview` instead.
- `quarto preview` — local live-reload preview server, and the right tool for rendering/iterating on just one page: it renders (and re-renders on save, via its own mtime-based file watcher) only the page you actually navigate to, not the whole site or its listing pages.
- `npm test` — runs `js/report-bug.test.js` and `scripts/analytics.test.js` (Node's built-in test runner). The `VM.*` unit tests moved to the mathviz repo with the code; run `npm test` *there* after editing a shared function. Requires `npm install` once first.
- `npm run verify:analytics` — real-browser test of the analytics consent flow (`_includes/analytics.html` + `_includes/consent.html`): banner display, Allow/No thanks, the footer reopen link, withdrawal, and Do Not Track/Global Privacy Control. Requires `docs/` to already be rendered. Fast to re-run on its own while iterating on consent copy or wiring, without paying for a full-site `npm run verify` crawl.
- `npm run verify` — `quarto render` then a headless-browser pass over **every** rendered page on the site (clicks every button, nudges every slider, asserts zero console/page errors). This is what actually catches a broken `VM.category.fn` call site — `quarto render` alone only catches Pandoc/parse errors, not OJS runtime errors. It's a full-site crawl (all pages, several minutes) — **only run it when the user explicitly asks for it**, not as the default post-edit check. See `.claude/skills/verify/SKILL.md` for the full two-tier verification approach and why it's structured this way.

**Default verification for a change scoped to one page**: `quarto preview` the project, then load just that page's URL (it renders on demand, nothing else) and check it there — for a scripted check, drive that same URL with a short one-off Playwright script, asserting zero `console.error`/`pageerror` while exercising its controls (see `.claude/skills/verify/SKILL.md`'s gotchas on why `file://` won't work and what to stub). Reach for the full `npm run verify` crawl instead only when the user asks for it, or the change updates the mathviz extension (a new tag touches every page; a single-page check can't catch a regression on a page it didn't look at).

There is no lint command. `package.json` is dev-only (Playwright for `npm run verify`) — nothing in it is shipped to `docs/` or affects the site's runtime; the site itself still has no bundler and no build step beyond `quarto render`. JS is served as static files, not bundled.

## Source vs. generated output

- Edit `.qmd`, `.css`, `_theme/`, `_includes/` and `js/report-bug.js`. **`docs/` is generated** — never edit it by hand; re-render instead. (`.gitignore` ignores `docs/`, though a prior build is still tracked.) **`_extensions/` is vendored, not authored**: it is what `quarto add apurvanakade/mathviz` copied in. Don't edit it here — change the mathviz repo, release, and `quarto update apurvanakade/mathviz@vX.Y.Z` (see the mathviz section below).
- **Releasing (`develop` → `main`): fast-forward only.** `develop` is where work lands; `main` is a pointer to the last published state, and pushing it deploys (see below). Release with `git checkout main && git merge --ff-only develop && git push origin main`, then `git checkout develop`. Do **not** squash-merge into `main`: a squash commit records no parent link back to `develop`, so the merge base between the branches never advances — every later merge re-diffs the entire branch from an ancient base and conflicts with content `main` already has (13 squash-merges had frozen the base at a commit 52 commits back, and the last one conflicted across 8 files with zero real divergence). If `--ff-only` is ever refused, the histories have diverged again; reconcile once with `git merge -s ours main` on `develop` (records `main` as an ancestor without changing `develop`'s tree) rather than force-pushing `main`.
- `.github/workflows/publish.yml` renders the site and publishes `docs/` to the `gh-pages` branch automatically on every push to `main`. `.github/workflows/deploy.yml` then deploys whatever is on `gh-pages` to GitHub Pages (triggered by pushes to that branch) — the two are separate workflows because `actions/deploy-pages` needs the already-rendered output as its own checkout ref.

## Branches and preview: one worktree per branch

**Never `git checkout` a branch inside a folder with a running `quarto preview`.** The preview's watcher treats a change to `_quarto.yml`, `styles.css`, or anything under `_includes/`/`_theme/` as invalidating every page (correctly -- the sidebar and `<head>` are baked into each one), and almost every feature branch touches at least one of those. A checkout rewrites them, so the watcher kicks off a full-site re-render (minutes) on every switch. Per-page laziness applies only to `.qmd` edits.

The fix is to not switch branches in place. `~/Documents/VisualMathLab` is the long-lived **`develop`** checkout and stays on `develop`; every other branch gets its own sibling folder via `git worktree`, with its own untracked `docs/`, `.quarto/`, and preview server on its own port. `git worktree list` shows which folder holds which branch.

There is a second, separate trigger with the same symptom: **on startup, `quarto preview` renders every input whose output in `docs/` is missing or older than the input** (`serveFiles` in Quarto's `serve.ts` compares mtimes; the `--render none` default only means "don't re-execute code", not "don't render"). So a brand-new worktree, whose `docs/` is empty, pays one full-site render the first time its preview starts -- expected, and once per worktree, not per switch. After that, startups only re-render what is stale. This is also why killing the preview *before* a checkout doesn't help much: the checkout still bumps the mtime of every `.qmd` that differs, and the next startup re-renders all of them.

1. **New feature branch**: `git worktree add -b app/<slug> ../VisualMath-<slug> develop`, then in that folder `quarto preview --port <unused port> --no-browser`. Use `4200` for develop and count up from `4201` for features -- one preview per worktree, never two in the same folder.
2. **Existing branch**: same command without `-b`. A branch can be checked out in only one worktree at a time; if git refuses, `git worktree list` shows where it already lives.
3. **Switching branches**: `cd` to the other folder (or switch browser tabs to its port). Nothing is rewritten, so nothing re-renders.
4. **Tests in a worktree**: `node_modules/` is per-folder, so run `npm install` once there (or `ln -s ../VisualMathLab/node_modules node_modules` -- `package.json` is identical across branches) before `npm test`/`npm run verify`.
5. **Landing**: merge into `develop` from the develop folder (or merge the PR and `git pull` there). Its preview will do one full re-render if the merge touched the project-level files above -- once per merge, not per switch.
6. **Cleanup**: stop that worktree's preview, then `git worktree remove ../VisualMath-<slug>` and `git branch -d app/<slug>`. Without stopping the preview first, `remove` complains about the untracked `docs/`.

If you ever must checkout or pull in a folder that has a preview, kill the preview first and restart it afterwards. That avoids the watcher's reaction to the project-level files, but the restart will still re-render every page whose `.qmd` the checkout touched (see above) -- there is no way to switch branches in place without paying for what changed.

## Analytics and consent

Usage analytics only — no ads signals, no remarketing, no Google Signals.

- `_includes/analytics.html` is the minimal GA4 snippet (~3kB, vendored from
  [dariusz.wieckiewicz.org](https://dariusz.wieckiewicz.org/en/minimal-google-analytics-4-snippet/)),
  talking straight to the Measurement Protocol v2 endpoint instead of loading
  gtag.js. The file's header comment lists every local deviation from
  upstream; keep that list accurate when re-vendoring a newer version.
- `_includes/consent.html` is the consent banner, plus the gate that actually
  runs the snippet. **Quarto's built-in `cookie-consent:` is deliberately not
  used** — its copy is baked into its bundle and claims the site shows
  personalized content and targeted ads, with a whole "Targeting and
  advertising cookies" section in its preferences center; there is no
  supported way to change those strings, its 34-language switcher would leave
  every other translation making the same false claim, and it weighs 207kB to
  gate a 3kB snippet. Don't reintroduce it.
- **The gate**: analytics.html ships as `<script type="text/plain"
  data-consent="analytics">`, which no browser will execute. consent.html
  re-creates it as a real `<script>` once the visitor allows analytics.
  Assigning to `.type` in place would not work — a script only runs when it is
  inserted. Don't "fix" that `text/plain` type; it is the gate.
- Both are loaded through `include-after-body`, **in that order** — consent.html
  searches the DOM for the script analytics.html emits, and the snippet reads
  `document.body`/`document.title` at call time, so neither belongs in
  `include-in-header`.
- The consent choice lives in `localStorage`, so **the site sets no cookies at
  all**. Global Privacy Control and Do Not Track are honoured as an answer
  already given.
- `privacy.qmd` (linked from the footer, alongside an "Analytics preferences"
  link that reopens the banner) documents exactly what is sent and what is
  stored. **It is a factual claim about the code**: if you change what the
  snippet collects or what is stored, change that page in the same commit.
- The snippet drops the query string from the reported page location. On this
  site a query string is the visitor's own math input (see the URL-shareable
  inputs section below), which doesn't belong in an analytics report and would
  fragment one page into hundreds of addresses.
- **Do Not Track / Global Privacy Control win over the footer link.** The
  snippet returns early on either signal even after consent, so a recorded
  "yes" would measure nothing; the reopened banner therefore says so and
  disables Allow rather than pretending. `privacy.qmd` states the signal
  wins; both test tiers assert it.
- **Third-party requests are part of the privacy surface**, and `privacy.qmd`
  has a "Third-party resources" section that names every host a page loads
  from (`cdn.plot.ly`, `cdn.jsdelivr.net` for math.js and Quarto's MathJax,
  `cdnjs.cloudflare.com` for Quarto's polyfill). the mathviz extension
  emits `<meta name="referrer" content="same-origin">` (`mathviz.referrer` in
  `_quarto.yml`, ahead of its own CDN tags) so none of them sees the
  page path or query string, and fonts are self-hosted (see the theme section
  below). Adding a CDN script — in `head-scripts.html` or via a new
  `mathviz:` option — means adding its host to that page; a Tier 1 test
  cross-checks the two by reading both files.
- Covered by both test tiers: `scripts/analytics.test.js` (Tier 1 — structural
  invariants on both files' contents, plus the snippet's client-side logic run
  against a stubbed DOM) and `scripts/verify-analytics.mjs` / `npm run
  verify:analytics` (Tier 2 — the consent gate itself in a real browser, since
  a `text/plain` script only fails to execute there, not in a stub). Update
  both when changing this wiring.

## Embed mode

Any app page loaded with `?embed=1` renders the app alone, for another site to put in an `<iframe>` (`embed.qmd` documents this for readers; the footer links to it). The pieces:

- An inline script at the top of `_includes/head-scripts.html` adds `vm-embed` to `<html>` — in `<head>`, before `<body>` exists, so the chrome never paints — and wraps `history.replaceState` so `embed=1` survives the URL rewrite every app does from its `committed`/`urlSyncControls` cells. The wrapper matters for a page that builds its query string from scratch (`apps/distribution-relationships/index.qmd`'s `new URLSearchParams()`) rather than from `location.search`; a page should still prefer the latter.
- `styles.css`'s "Embed mode" section hides the navbar, sidebar, glass, rail, title block, footer, page navigation, consent banner, mobile warning and report-bug popup on `html.vm-embed`, and zeroes the fixed-navbar body padding.
- `consent.html`, `mobile-warning.html`, `sidebar-rail.html` and `js/report-bug.js` each return early on `html.vm-embed`. Consent's early return is a privacy claim: an embedded app never shows the banner and never runs analytics, even for a visitor with a stored "yes" — `privacy.qmd` says so, `scripts/verify-analytics.mjs` section 7 tests it.
- GitHub Pages sends no `X-Frame-Options`, so nothing server-side is involved. Adding a new site-chrome element means adding it to the `html.vm-embed` selector list.

## Architecture

Each app page (`apps/<slug>/index.qmd`, e.g. `apps/newton-method/index.qmd`) is a self-contained interactive app. There is no `method.js` per page — all method logic and rendering live directly in named OJS cells inside the `.qmd`:

1. `_quarto.yml`'s `filters: [mathviz]` runs the vendored extension's filter on every page, which puts math.js, Plotly, `mathviz.js` and `mathviz.css` into `<head>` — in that order, and *ahead of* everything in `include-in-header` — exposing `window.VM` (see the mathviz section below). `_includes/head-scripts.html` then adds only what is this site's own: the self-hosted fonts stylesheet, the embed-mode script, and `js/report-bug.js`. Every page gets all of this for free — no per-page script block is needed.
2. `result` — runs the numerical method with the current inputs (e.g. Newton, bisection, fixed-point) and returns `{rows, f, ...}`. `rows` is the full iteration history; each page's `result` cell already reads like plain imperative code (`while` loop, explicit early returns) rather than a functional pipeline.
3. `setup` — derives the data shared by the plots below from `result`: which rows are visible at the current step, axis ranges, and a sampled curve for the smooth function trace.
4. `mainPlot` — builds the primary Plotly chart. It's a closure over a `_plotDiv` variable so the same DOM node is reused across reactive re-renders (`Plotly.react` instead of `Plotly.newPlot` after the first render) — this is what preserves user zoom/pan when the step slider moves.
5. `iteratesPlot`, `convergencePlot` — Observable Plot charts covering the entire run (not just the current step), shown in an **open-by-default** "Convergence plots" callout (`::: {.callout-note collapse="false" title="Convergence plots"}`). They're diagnostic content worth seeing without an extra click, unlike the raw data dump below.
6. `iterationTable` — builds a DOM table via `VM.ui.renderTable`, shown in a **collapsed-by-default** "Iteration table" callout (`collapse="true"`) — raw per-row data, useful on demand but not something to lead with.

OJS cells wire Quarto `Inputs.*` controls (function text, initial guess/endpoints, max iterations) → `result` → an `Inputs.range` step slider → `setup` → `mainPlot(setup)`. OJS reactivity re-runs everything downstream when any input changes.

### Theme, design tokens, and site chrome

`_theme/vml-light.scss` / `_theme/vml-dark.scss` (wired in as `format.html.theme.light`/`.dark` in `_quarto.yml`) own this site's look. The `--vm-*` tokens themselves are *defined* by mathviz (`tokens.css`, zero-specificity `:where()` defaults, so anything declared here wins regardless of load order); these two files override every chrome token with the site's values, add `--vm-font-sans` (Inter, so charts are typeset like the page), and alias the four palette hues page-local CSS names in prose (`--vm-alt: var(--vm-color-alt)` etc. — repeated in *both* files, because a `var()` inside a custom property resolves on the element it is declared on, and the dark palette matches `<body>`, not `<html>`). The chart palette (`--vm-color-fn/alt/ok/muted/ink/warn/accent2/accent3/halo`) is not redeclared here: mathviz's defaults *are* this site's palette. Each has two layers: `scss:defaults` sets Bootstrap's own `$variables` (`$body-bg`, `$link-color`, `$border-color`, `$font-family-sans-serif`, ...) so Quarto's built-in chrome (navbar, cards, callouts, tables) inherits the palette, and `scss:rules` re-declares the same values as runtime `--vm-*` custom properties (`--vm-bg`, `--vm-surface`, `--vm-text`, `--vm-text-soft`, `--vm-border`, `--vm-accent`, `--vm-accent-hover`, `--vm-grid`, `--vm-radius`, `--vm-shadow`, plus `--vm-alt`/`--vm-ok`/`--vm-warn`/`--vm-accent2` — CSS copies of the matching `VM.plotting.colors()` entries, for the few places prose or chrome has to name a chart color: an invalid-field border, a `.vm-swatch` in a sentence) under `body.quarto-dark`/light default, since those also have to be readable at runtime by JS (mathviz's `chart-theme.js` reads them via `getComputedStyle` to theme Plotly/Observable Plot charts — a Sass variable is compile-time-only and doesn't survive into the page). `styles.css` consumes only `--vm-*` — never a raw hex, never a `--bs-*` fallback chain — so re-theming the site is a two-file edit. Fonts are Inter (body/UI) + JetBrains Mono (code), **self-hosted** from `fonts/` (`fonts/fonts.css` holds the `@font-face` blocks, linked from the top of `_includes/head-scripts.html`; `_quarto.yml`'s `project.resources` copies the folder into `docs/`). They used to come from Google Fonts — don't put that back: a Google Fonts request hands Google every visitor's IP address before consent, which is the thing a German court ruled a GDPR violation, and `privacy.qmd` now states that no font request goes to Google. The header comment in `fonts/fonts.css` says how to refresh the files.

The sidebar (`#quarto-sidebar`) is forced off-canvas at *every* width (not just Quarto's own sub-992px behavior) via `styles.css`, and driven by `.vm-sidebar-open`/`.vm-sidebar-pinned` classes on `<body>` that `_includes/sidebar-rail.html` owns — a small always-visible rail at the left edge (click the hamburger to open, click-to-pin, `Escape`/click-outside to close, pin state in `localStorage`) — deliberately **no** hover-to-preview: opening on pointer drift into the left edge churned `<body>`'s class list (see the `onThemeChange` guard in mathviz's `chart-theme.js`) and forced the rail's box to span the viewport, which left an invisible strip over the content column below 768px rather than Bootstrap's own `.collapse`/`.show` machinery, which this bypasses entirely. `#vm-sidebar-rail` is inserted at runtime, not server-rendered.

### The mathviz extension (`_extensions/`)

Everything a second site could reuse — the `VM.<category>.<fn>` utilities (`expressions`, `numerical`, `sampling`, `filters`, `distributions`, `plotting`, `ui`, `discreteMath`), the `ojs-*`/`vm-*` design-system CSS (panels, chart block and fullscreen chain, floating legend, slider bar and play button, modebar, swatches, iteration table) and the `--vm-*` token defaults — is the **mathviz** library, [apurvanakade/mathviz](https://github.com/apurvanakade/mathviz), and its `CLAUDE.md`/README document every function and every class. It reaches this site as a Quarto extension:

- **Install/update**: `quarto add apurvanakade/mathviz@vX.Y.Z` writes `_extensions/apurvanakade/mathviz/` (the Lua filter plus the built `dist/mathviz.{js,css}`); `_extensions/` is committed, so `publish.yml`'s plain `quarto render` needs no install step. `quarto update apurvanakade/mathviz@vX.Y.Z` to move to a newer tag by hand — but normally you don't: `.github/workflows/update-mathviz.yml` runs on every push to `develop`, compares `_extension.yml`'s `version:` with the newest `vX.Y.Z` tag on the mathviz repo, and if it's behind runs that same `quarto update` and commits the result to `develop` as `github-actions[bot]`. So after tagging a mathviz release, push anything to `develop` (or run the workflow from the Actions tab) and `git pull` before the next `--ff-only` release. **To try an unreleased library change here first**: `quarto add /path/to/mathviz --no-prompt` accepts a local checkout (it copies, so re-run after each `npm run build` there; a symlink at `_extensions/mathviz` is not discovered by Quarto), then put the tagged install back before committing.
- **Wiring** is two keys in `_quarto.yml`: `filters: [mathviz]` and `mathviz: {referrer: same-origin}`. The filter emits `<meta name="referrer">`, then the math.js and Plotly CDN tags, then `mathviz.js` and `mathviz.css`, all as html dependencies — which land in `<head>` *above* `include-in-header`. That is why the referrer meta moved out of `head-scripts.html` into the extension's options: emitted from the include, it would come after the CDN tags it exists to cover. `scripts/analytics.test.js` asserts the option is set and derives the third-party hosts `privacy.qmd` must name from the extension's Lua file; `scripts/verify-analytics.mjs` asserts the rendered order.
- **Changing a shared function or a design-system rule** means editing the mathviz repo (`src/js/**`, `src/css/**`), `npm test && npm run build` there, tagging a release, and updating the tag here — a separate commit in each repo. Don't patch `_extensions/**` in place: the next `quarto update` would discard it silently.
- **Site-specific JS stays here**: `js/report-bug.js` (hardcodes this repository and maps a page URL onto its `.qmd` path — meaningless elsewhere) is the whole of `js/` now, loaded from `head-scripts.html`, with its test next to it. A utility used by exactly one page stays with that page (`apps/polynomial-interpolation/cubic-spline.js`, loaded by a page-level `include-in-header` that Quarto merges with the project-level one); promote something into mathviz only once a second *site* — not just a second page — needs it, or once it is generic enough that one plausibly would.
- **Page-level conventions that depend on the library** — the `vmTheme`/`chartColors` reactive pair, `showlegend: false` on every trace, `VM.plotting.emptyState` for an unparseable formula, `chartColors;` as a bare dependency line in cells that store a `VM.discreteMath.*Color` result — are described in the sections below and in the mathviz README; `apps/newton-method/index.qmd` is the reference wiring.

### Site structure: `apps/` and `topics/`

The whole site is exactly one level deep. There is no topic folder holding its own pages, no subtopic level, and nothing nested three deep:

- **`apps/<slug>/index.qmd`** — every interactive app and expository page, 20 as of this writing, all siblings under one flat folder. A page's `topic:` front-matter field (e.g. `"Root Finding"`, `"Sperner's Lemma"`) is what a topic listing page filters on — it must equal that topic page's `title:` exactly.
- **`topics/<topic>/index.qmd`** — one listing page per topic (Root Finding, Piecewise Interpolation, Differential Equations, Sperner's Lemma, Model Fitting, Probability), each a `listing:` with an explicit `contents:` array of that topic's `../../apps/<slug>/index.qmd` paths, `sort: "order"` (an app's `order:` front-matter field, not upload date). **Not** a glob and **not** `include: {topic: ...}`-filtered — Quarto's `listing.include` only matches its own built-in fields, not an arbitrary custom one like `topic:`, so a filter on it silently returns everything unfiltered (verified: it rendered all 19 apps on every topic page). `topic:` still lives in each app's front matter as documentation of which topic page lists it, but adding a page means adding its path to that topic's `contents:` array by hand — there's no auto-discovery. There is no intermediate `computational-math/`, `discrete-math/`, or `data-science/` folder, and no subtopic folder — `probability/bayes/` and `probability/recursive-filters/` (two extra listing pages that existed only to group two apps each) were removed; Bayes' theorem and recursive filters are now just two `## `-level paragraphs inside `topics/probability/index.qmd`. Those broader areas (Computational Math, Discrete Math, Data Science) exist only as a `categories:` tag on each app page — there's no page or folder for the area itself.
- `_quarto.yml`'s sidebar lists every app explicitly, grouped under its six topics — an explicit list, not a glob (`apps/*/index.qmd` can't be filtered by topic in a sidebar `contents:`), and the order there is what drives `page-navigation` prev/next.
- `bread-crumbs: false` in `_quarto.yml`, deliberately: with one level of nesting there's nothing meaningful to trace, and Quarto gives an href-less sidebar `section:` the href of its first child — a plain-text grouping label used to render as a breadcrumb crumb that linked to the wrong page.
- `project.render: ["*.qmd", "**/*.qmd"]` in `_quarto.yml` is an explicit allowlist — without it Quarto also compiles the repo's own `CLAUDE.md`/`CONTRIBUTING.md`/`README.md` into published site pages.

### URL-shareable inputs and example presets

Most computational-math pages (e.g. `apps/newton-method/index.qmd`, `apps/numerical-integration/index.qmd`) make their state shareable via the URL's query string, and pair that with a "Try an example" dropdown near the top controls:

1. Each input cell reads its default value straight from `new URLSearchParams(window.location.search)` inline, falling back to a hardcoded default (e.g. `params.get("f") ?? "x^2"`) — so loading the page with `?f=...` pre-fills the field.
2. A `committed` cell — the one that actually feeds `result` — snapshots the current field values only when the Plot/Regenerate button fires (it reads the stable `viewof x` DOM views, not the reactive `x` values, so it does not rerun on every keystroke) and writes them back into the URL via `history.replaceState(null, "", ...)`, so the address bar is always a reproducible link to the current run. On pages with additional always-live controls that aren't gated behind a commit button (step counts, method checkboxes, etc. — see `apps/numerical-integration/index.qmd`), a separate `urlSyncControls` cell reactively keeps those in the URL too, alongside `initial<X>` helper cells that parse them back out on load.
3. An `examples` cell holds a single array `[{title, params}, ...]` of preset inputs. A `viewof exampleSelect` — `Inputs.select([null, ...examples], {label: "Try an example", format: e => e ? e.title : "Pick an example…", value: null})` — sits near the top controls (the leading `null` is a placeholder so nothing applies on load). An `applyExampleFromSelect` cell attaches a **one-time native `"change"` listener** to `(viewof exampleSelect).querySelector("select")` (not an OJS cell reactive on `exampleSelect`'s value — see the gotcha below) that reads `(viewof exampleSelect).value` and calls `VM.ui.applyExampleParams(exampleFieldSelectors, example.params, viewof plotTrigger)`, which sets each field's view and clicks Plot/Regenerate in place — no page navigation, so no reload and no scroll jump. There is no bottom example gallery/grid — the dropdown is the only way to load a preset. See mathviz's `src/js/ui/apply-example.js`.

**Every input on the page must be wired into the URL whenever possible** — not just the function/endpoint fields gated behind the commit button. Step counts, method checkboxes, and any other always-live control need both an `initial<X>` cell reading it back out (step 1) and an entry in `committed`/`urlSyncControls` writing it back (step 2), the same as `apps/numerical-integration/index.qmd`'s `initialN`/`initialMax`/`initialMethods` + `urlSyncControls`. For a checkbox group, add a slug↔label `Map` pair (`methodSlugToLabel`/`methodLabelToSlug`) so the URL uses short stable slugs instead of the human-readable labels verbatim. An example's `params` object is a contract: every key it sets must actually appear in `exampleFieldSelectors`, or the example silently doesn't do what it claims — worth checking on any edit. (`apps/explicit-ode-methods/index.qmd` shipped for a while with `n`/`max`/`show` params on every example that no cell ever read, back when examples were a hand-written `<div class="example-grid">` of `<a href="?...">` links — that pattern is retired; don't reintroduce it.)

Two non-obvious gotchas in this wiring, both found the hard way (see mathviz's `src/js/ui/apply-example.js` comments for the full explanation):

- `exampleFieldSelectors` values are `data-example-field` CSS selectors (plain strings tagged onto each `viewof` cell's returned element), not direct `viewof` references. When a field's bounds reactively depend on another field (e.g. a step slider capped by a "max" field), OJS recreates that field's `viewof` cell whenever the upstream field changes. A cell that references such a view by name becomes reactive on it — and since applying an example is what changes the upstream field, a direct-reference version re-triggers itself in an unbounded loop (a real one was caught here: writing "max" recreated the "n" slider's view, re-triggering the apply cell, which wrote "max" again — until Chrome's history-API throttling kicked in). List an upstream field (e.g. "max") before any field that depends on it (e.g. "n") in `params` — `applyExampleParams` applies params in object order with a 100ms yield between each (measured: OJS's own reactive updates settle in ~40ms, not one tick), giving a recreated view time to exist before the dependent field is applied.
- The dropdown's trigger must be a plain DOM event listener attached once (the `enterToPlot` pattern), never an OJS cell reactive on `exampleSelect`'s value — a native `<select>` fires both `input` and `change` per selection, so a reactive cell runs twice, and the two overlapping calls race (this corrupted a field's final value in practice).

### Chart controls: floating legend, attached slider bar

Every control that's *always-live* (reacts immediately, no Plot/Regenerate button gating it) and whose only job is to change what the chart currently shows — a trace-visibility legend, a step/iteration scrubber, a model parameter like `n` or a filter's α/R/Q — belongs with the chart rather than in the controls panel further down the page. This is a uniform layout convention, not a per-page style choice: it's what's left every single `panel-tabset` on the site collapsing (see below), since in every case the second tab turned out to be exactly this category of control.

**The two live in the chart's wrapper but not in the same way, and the difference is the point.** The legend genuinely floats over the plot: it's small, it hugs a corner, and it's draggable, so the reader can move the one thing it covers. The slider bar does **not** float — it sits in normal flow directly *above* the chart, inside the same wrapper. It used to be pinned over the chart's bottom edge like the legend, and that was a mistake: a full-width bar parked across the bottom of a plot covers exactly the region a reader scrubbing a step slider is watching, and it covers it *permanently*, on every page, for every reader. Translucency, a collapse button and drag-to-move were all considered and rejected as ways to paper over that — each one asks the reader to keep managing a problem the layout created. Reserving the space instead means the chart is never obscured at all, and costs only the bar's own height, which `.plotly-box-large`'s 72vh (down from 78vh) gives back.

**Above the chart rather than below it**, because every other control on the page — the whole `.ojs-panel` — is above it, so a bar underneath left the reader's eye travelling past the chart and back again to find it. Reading order is now panel, sliders, chart. That order is set with flexbox `order` on `.ojs-chart-block` rather than by moving the div in all 14 pages' markup, which also keeps the bar inside the wrapper, where fullscreen needs it. One consequence worth knowing: the legend is absolutely positioned, and its containing block used to be `.ojs-chart-block`, whose top edge *was* the chart's top edge — with the bar above, it no longer is, and the legend would sit on the sliders. The legend's own (zero-height) cell is therefore ordered between the bar and the chart and made the containing block, which puts the legend back at the chart's top-left corner with no JS and nothing to keep in sync with the bar's height. That in turn requires switching off `.cell-output-display`'s `overflow: auto` for that one cell, or the wrapper clips the legend to a zero-height box, i.e. to nothing — the same trap mathviz's `slider-play.js` popover hit, solved there with the top layer.

1. Wrap the page's `mainPlot` cell in `<div class="ojs-chart-block">` (`position: relative` in mathviz's `chart-block.css`, the positioning anchor for the legend). Fullscreening a chart via the shared modebar button (mathviz's `plotly-fullscreen-button.js`) fullscreens this wrapper rather than the bare Plotly div when present, so everything inside it — legend and sliders alike — stays visible in fullscreen. **That is also why the slider bar goes inside this wrapper even though it no longer floats**: a bar that were merely a sibling of the wrapper would vanish the moment a reader fullscreened the chart. In fullscreen the wrapper becomes a flex column so the chart takes the height the bar leaves; the chart's letterboxing measures itself against that remaining box via container-query units (`100cqh`/`100cqw`), not `100vh`/`100vw`, which would overstate the available height by the bar's own and stretch the chart wider than its on-page aspect ratio.
   - **A page that draws its own SVG (Observable Plot, or a hand-built `<svg>`) instead of a Plotly chart gets no modebar, so it gets no fullscreen button from that patch.** Add `ojs-svg-block` next to `ojs-chart-block` on the wrapper (`<div class="ojs-chart-block ojs-svg-block">`, holding the `.ojs-chart-controls` bar and the drawing cell) and mathviz's `svg-fullscreen-button.js` does the rest — see its entry in the mathviz CLAUDE.md. Nothing else is page-specific: no button cell, no page-local CSS, no aspect ratio to record. Every Sperner's Lemma app and `apps/positive-predictive-value/index.qmd` are wired this way; `apps/sperners-lemma-geometric-proof/index.qmd` is the one with a wrinkle worth knowing (two captioned plots side by side in one cell — its page-local `<style>` keeps that pair a row in fullscreen, spelled with both block classes because the shared chain rule ends in `:has()`, which counts its argument's specificity). The opt-in is a class rather than auto-detection ("any block without a Plotly chart") because OJS renders cells asynchronously — at load time a Plotly page's block has no chart in it yet either. A page-level floating element appended to `<body>` (the PPV page's hover tooltip) must be reparented into `document.fullscreenElement` while fullscreen is active: the Fullscreen API paints only the fullscreened subtree on top, and a body child sits *under* it whatever its z-index.
2. A trace-visibility legend (`viewof <name> = VM.ui.legendOverlay(...)`, mathviz's `legend-overlay.js`) is a direct sibling of the `mainPlot` cell inside that wrapper, floating top-left via `.ojs-legend-overlay`. **This replaces Plotly's built-in legend, it doesn't sit alongside it** — every trace `mainPlot` pushes carries `showlegend: false`, so Plotly draws no legend of its own (with two or more traces it otherwise auto-shows one, in Plotly's default style, in the top-right corner — visibly not this site's chrome). The wiring, copied verbatim across pages (`apps/newton-method/index.qmd` is the reference): a `traceOptions` cell listing the labels in display order, a `traceColors` `Map` from label → the exact color `mainPlot` draws that trace in (so the swatches double as a color key), one `show<Trace> = traces.includes("<label>")` `//| output: false` cell per trace, and `mainPlot(setup, ...show<Trace>)` gating each `data.push` on its flag — a hidden trace is never pushed, rather than pushed with `visible: false`.
   - **When the trace set is decided at runtime** (a page where selecting something changes *which* distributions/series are drawn, e.g. `apps/distribution-relationships/index.qmd`), the fixed wiring above doesn't apply: there is no static `traceOptions` list and no way to write one `show<Trace>` cell per trace. Derive the `[{label, color}]` array in a cell instead and pass it straight to `legendOverlay`, then have the plot cell skip any series whose label isn't in the view's value — same contract (`showlegend: false` on every trace, a hidden trace never pushed), just computed. Two things to get right: keep the labels **stable** (a label carrying a parameter value rebuilds the legend on every slider move, which flickers and silently discards whatever the reader had toggled off — put the values in the trace's Plotly `name`, which only shows on hover), and hide the panel when it has no rows via `:not(:has(.ojs-legend-item))` rather than `:empty`, since `draggable-overlay.js` appends its grip as a child and `:empty` therefore never matches.
   - A page whose *controls* are likewise dynamic has to build them in one cell, which puts Quarto's own output wrappers between `.ojs-chart-controls`'s grid and the sliders, so the grid sees one child and stacks them in a column. Make that cell's own container the grid (`display: grid` with the same `auto-fit` track) rather than collapsing the wrappers with `display: contents` — the wrapper class names (`.cell-output-display`, `.ojs-in-a-box-waiting-for-module-import`) are generated markup no page should depend on. Keep `.ojs-grid` on the controls div so mathviz's label-above-track rule (`panel.css`), which matches forms at any depth, still applies.
3. Every always-live slider is a further sibling, wrapped in `<div class="ojs-chart-controls">` (mathviz's `legend-controls.css`) — a normal-flow block directly above the chart, spanning its width, wearing `.ojs-panel`'s solid `--vm-surface` chrome rather than the legend's blurred translucent card (there's no curve behind it to show through any more). **The bar holds sliders and nothing else** — with one deliberate exception: a small always-live control whose only job is to change what the chart currently shows (the PPV page's Shuffled/Sorted radio, the Sperner apps' "Regenerate colors" button) may sit at the bar's right end as the `.ojs-row`'s last div, since a controls panel holding nothing but that one button would be silly; a *text field* never does. A text field that bounds one (every page's "Max"/"Max steps"/"Max depth") used to share the bar with its slider; it lives in the controls panel now, in its own group below the commit-gated fields, still always-live. Keeping the two apart is what leaves room for the play button (mathviz's `slider-play.js`, which enhances every slider automatically — no per-page wiring, no speed field) that sits inline at the left of a track, and the same separation holds in a panel: no `.ojs-row`/`.ojs-grid` group anywhere mixes a range slider with a text box. A bar with two or more sliders (e.g. `apps/recursive-filters-1d/index.qmd`'s four filter parameters) additionally stacks each one's label above its track — the same layout `.ojs-panel` already uses — via a rule scoped to `.ojs-chart-controls.ojs-grid`, since the auto-fit grid track otherwise leaves too little width for label, track, readout, and the play button side by side.
   - A single slider: no layout primitive at all (`<div class="ojs-chart-controls">`), since there is nothing to lay out against.
   - Three or more controls (e.g. `apps/recursive-filters-1d/index.qmd`'s four filter-parameter sliders): combine with `.ojs-grid` instead (`<div class="ojs-chart-controls ojs-grid">`), which auto-wraps into multiple rows on narrow viewports rather than cramming everything into one line.
   - Any `//| output: false` helper cell these sliders depend on (a `maxN`/`tolerance`/`maxSteps` parser) is declared just above `.ojs-chart-block` opens, not inside the row/grid div — an output:false cell placed inside an `.ojs-row`/`.ojs-grid` still emits a real (zero-size) `.cell` node that counts as a flex/grid child and steals the first-child/last-child (or column) layout meant for a visible sibling.
4. `data-example-field` tagging still works with a field in the controls bar exactly as it does for a field in the panel — `document.querySelector` finds it in the DOM regardless of where it sits (see the example-dropdown wiring below).
5. **The legend is draggable, for free.** mathviz's `ui/draggable-overlay.js` finds every `.ojs-legend-overlay` inside an `.ojs-chart-block` and gives it a grip (revealed on hover at the panel's right edge) that moves it off whatever part of the curve it's covering, clamped to the chart, remembered per page in `localStorage`, double-click or `Home` to reset. A new page needs no wiring: don't call anything, and don't hand-position the legend to dodge a curve. **The slider bar is deliberately not in that selector** — it covers nothing, so there is nowhere to drag it to, and leaving it out is also what stops an offset stored back when it *did* float from shoving the in-flow bar out of place (this module is the only thing that ever writes `transform` on these panels, so a bar it never touches simply renders where the stylesheet puts it, and the stale entry is inert rather than actively wrong). Two things to preserve if you touch this: the grip is `position: absolute` so it takes no `.ojs-grid` track, and `styles.css`'s `.ojs-row > div:first-of-type`/`:last-of-type` sizing must stay `-of-type` — as `:first-child`/`:last-child` (which it was) *any* inserted non-div sibling stops it matching at all, since that reads "a div that is also the first child", not "the first div". This is the same trap as the `output: false` note in 3 above, one step further along.

**A page's remaining controls panel holds only what's left**: text fields gated behind a commit button (function, endpoints, initial conditions), the example dropdown, the Plot/Regenerate button, and any button-triggered action (e.g. `apps/l1-vs-l2-regression/index.qmd`'s "Regenerate points"). Below those, in its own `.ojs-grid` group, sits the always-live "Max"/"Max steps"/"Max depth" text field that bounds the chart's slider. Reading top to bottom the panel is then *what to compute*, then *how far the sweep runs*; see `apps/newton-method/index.qmd` for the reference wiring. (There is no separate "Play step"/speed field anymore — mathviz's `slider-play.js` derives playback speed from the slider's own range, and the reader picks a multiplier from the popover on the play button itself.)

### Tabbed controls

`::: {.panel-tabset}` (Quarto/Bootstrap nav-tabs) is available for when a page's controls form two or more distinct groups that *aren't* reducible to "static panel fields + always-live chart-controls sliders" above — but as of this writing no page on the site actually needs it: every prior tabset (`apps/explicit-ode-methods/index.qmd`'s "Inputs"/"Display Options", `apps/recursive-filters-1d/index.qmd`'s "Signal & Sampling"/"Filter Parameters", every Root Finding app, etc.) turned out to be exactly "panel fields" vs. "sliders that belong with the chart," and collapsed to a single `ojs-panel` once those sliders moved into the chart-controls bar. Before reaching for a tabset on a new page, check whether the second group is actually just sliders/legend toggles that belong with the chart — if so, use the pattern above instead, not a tab. A page whose controls are genuinely a single group (e.g. `apps/l1-vs-l2-regression/index.qmd`, `apps/butcher-tableau/index.qmd`, and now every other interactive page on the site) has nothing to split and stays as one plain `ojs-panel`; don't force a single-tab tabset just for consistency's sake.

If a future page does have a genuine second group, the tabset is wired to a `tab` URL query param, same spirit as every other input:

1. A `tabSlugToLabel`/`tabLabelToSlug` `Map` pair (short URL slugs ↔ the tabs' visible `## Heading` text), defined near the page's other URL-parsing cells.
2. Each tab is a `## <Tab Name>` heading directly inside the `::: {.panel-tabset} ... :::` block, with that tab's `ojs-panel` div(s) as its content.
3. A `tabSync` cell — placed after the page's other URL-sync cells (`committed`/`urlSyncControls`) — that activates the URL-requested tab on load via Bootstrap's `Tab` API (`window.bootstrap`, already loaded by Quarto's theme) and, on `shown.bs.tab`, writes the newly active tab's slug back into the URL with `history.replaceState`. It matches tabs by their visible label text (`link.textContent.trim()`), not Quarto's auto-generated element IDs (e.g. `tabset-1-1`), which aren't stable identifiers to build a URL contract on. No page currently has one to copy verbatim — check git history (e.g. `git show <commit>:apps/newton-method/index.qmd` from before this pattern was retired) for a worked example.

Fields tagged with `data-example-field` keep working across tabs with no extra wiring: `document.querySelector` finds them in the DOM regardless of which tab is currently visible, so an example dropdown living in one tab can still set fields that live in another.

### Adding a new method page (Root Finding, Differential Equations, Piecewise Interpolation, or any other computational-math topic)

1. Create `apps/<slug>/index.qmd` — `cp -r apps/_template apps/<slug>` (a working fixed-point-iteration starter with every shared cell and a `TODO` at each thing to change; Quarto ignores the underscore-prefixed original, so it is never rendered or listed) or copy a finished page (e.g. `apps/newton-method/index.qmd`), and adapt its `result`, `setup`, `mainPlot`, `iteratesPlot`, `convergencePlot`, and `iterationTable` cells to the new method's math and input fields. All `VM.*` utilities, the design-system CSS and the CDN scripts are already on every page via the mathviz extension — no per-page script block needed. Give it `topic: "<Topic Name>"` matching an existing topic page's `title:` exactly (or a new one, see step 3), a `categories:` list describing the method including `Computational Math` as one entry, and a one-sentence `description:` in plain text (no math markup — it's excerpted verbatim onto the page's listing card; without one, Quarto falls back to the page's first prose paragraph, which on these pages is the trailing explanation, not a summary). Use title-case capitalization for every category, matching the rest of the list. Listing pages render `categories: false` (see Conventions below) — the `categories:` list itself is metadata/search fodder, not something rendered as pills.
2. Give the front matter an `order: <n>` field one higher than the current last app in that topic. Two places need a manual one-line addition — neither auto-discovers the new page: the topic page's `listing.contents` array (`topics/<topic>/index.qmd`) and `_quarto.yml`'s sidebar (`apps/<slug>/index.qmd` under the right topic's `section:`, which also drives `page-navigation` prev/next order). The homepage's `Latest` listing (`contents: "/apps/*/index.qmd"`) *does* pick it up automatically, since that one is a real glob.

User-entered expressions are evaluated in-browser. Use `VM.expressions.makeFunction`/`VM.expressions.makeDerivative` (they handle normalization and error catching, returning `null` on a bad expression) rather than calling math.js directly. Currently, invalid input just makes `result` return empty `rows` (blank chart, empty table) — there's no surfaced error message to the user yet.

### Adding a new expository/proof page (Sperner's Lemma, or any future non-computational-math topic)

An expository page lives in `apps/` exactly like an interactive one — there is no separate folder for prose pages — and takes the same steps as above with one addition:

1. Create `apps/<slug>/index.qmd`. Give it `topic:` matching an existing (or new) topic page's `title:`, a `categories:` list including the area tag (e.g. `Discrete Math`) as one entry, and a one-sentence `description:` (see the computational-math section above — same reason, same convention). Use title-case capitalization for every category, matching the rest of the list.
2. Give the front matter an `order: <n>` field (reading order within the topic; these pages are proof/exposition steps, not independent methods, so order matters more than for computational-math topics).
3. If this is a brand-new topic (not just a new page under an existing one), also create `topics/<topic>/index.qmd` — copy `topics/sperners-lemma/index.qmd`'s front matter and replace `listing.contents` with the new topic's own `../../apps/<slug>/index.qmd` paths (an explicit list, not a glob — see the site-structure note above), add a homepage tile in `index.qmd`'s "Browse by topic" section, and add a `section: topics/<topic>/index.qmd` entry with its `contents:` list to `_quarto.yml`'s sidebar. There is no separate "broad area" page or folder — Computational Math / Discrete Math / Data Science / Probability exist only as `categories:` tags on the app pages themselves.
4. Not every page needs interactivity — `apps/barycentric-coordinates/index.qmd` and the proof pages mix substantial static exposition with one or two `{ojs}` apps, unlike computational-math pages which are interactive-app-first with prose secondary.

## Math exposition conventions

Patterns established across the Sperner's Lemma proof pages, worth reusing for future proof/exposition content rather than reinventing per page:

- **Crossref-labeled theorem/definition callouts**: `::: {#thm-name}\n...\n:::` (also `#def-`, `#cnj-` for conjectures/claims still to prove, `#cor-` for corollaries), referenced elsewhere in the same or other pages via `@thm-name` — Quarto resolves these to numbered links ("Theorem 1") automatically. Pick a short, descriptive slug (`#thm-sperner-local`, not `#thm-1`) since it's also the anchor.
- **Scaffolded exercises**: a `::: {.callout-tip title="Exercise"}` with the claim to prove (referencing it via `@cnj-name` rather than restating it) and numbered sub-steps, followed by one or more `::: {.callout-note collapse="true" title="Hint for step N"}` / `title="Solution sketch"` callouts a reader has to click to reveal. See `apps/sperners-lemma-combinatorial-proof/index.qmd`'s proof of `@cnj-bottom` for the full pattern. Don't put a crossref inside a callout's `title="..."` attribute itself (e.g. `title="Exercise: prove @cnj-bottom"`) — Quarto doesn't resolve crossrefs inside raw attribute strings, only in rendered body content, so it leaks through unprocessed; put the crossref in the callout body instead.
- **Color words in prose**: when a sentence names a color the diagram draws ("the red vertex", "RGB triangles"), tint the word with `<span class="vm-swatch vm-swatch-alt">red</span>` (mathviz's `swatch.css`; modifiers `-alt`/`-ok`/`-accent`/`-warn`/`-accent2`, named for the palette token so the swatch is the same hue as the dot or fill it describes, in both themes). Never an inline `style="background-color:red"` — a CSS named color is not the site's red and stays put when the theme flips. A page needing a shade the modifiers don't cover (the geometric proof's light/dark orientation hatches) defines its own class in its page-local `<style>` on top of `.vm-swatch`, still in `--vm-*` terms.
- **Plot figures are diagrams, not graphs**: a triangulation gets `axis: null` on both scales and `grid: false` (through `VM.plotting.plotOptions`, which otherwise turns the grid on), and a height computed from the width so a unit-wide equilateral triangle is drawn to scale — Plot stretches `y` to whatever height it is given. Strokes are `chartColors.ink`, a hollow marker's fill is `chartColors.halo`, never `"black"`/`"white"`.
- **References**: a `## References` section near the end, plain Markdown citations with inline links (author, title, venue, year, URL) — see `apps/sperners-lemma-geometric-proof/index.qmd` for the existing example. No BibTeX/CSL setup in this project yet.
- Interactive apps embedded in an expository page follow the same shared-palette conventions as any other page (`VM.discreteMath.*` for triangle/edge coloring, etc.) — exposition pages aren't exempt from the shared-library rule just because they're prose-heavy.

## Conventions

- TOC is **off** site-wide (`toc: false` in `_quarto.yml`): most app pages have no `##` headings at all (the app is the page), and listing pages have none either, so the default TOC was an empty rail. App pages never opt in, even the few with several `##` sections (`positive-predictive-value`, `sperners-lemma-geometric-proof`) — every app gets the same wide, centered body column, no right-hand rail. The only page with `toc: true` is `privacy.qmd`, a plain reference document. Don't add `toc: false` anywhere; it's already the default.
- Listing pages do **not** render `categories: true` (retired — 53 distinct one-off category strings across 20 pages made the rendered category rail and per-card pills unusable clutter, not a real filter). A listing's `fields:` list accordingly omits `categories` too. Front-matter `categories:` itself stays on every leaf page — it's still real metadata (search, potential future use) — it's only the *rendered* rail/pills that are gone. `_quarto.yml`'s `title-block-categories: false` matches this by suppressing the pill row Quarto would otherwise render under every page's `<h1>`.
- Every new code/content file must begin with the copyright/license header for its file type — see `CONTRIBUTING.md`. Authorship is per-file and per-contributor; add your name to `Authors:` for significant additions.
- **CSS used by exactly one page stays with that page, not in `styles.css`.** `styles.css` is this site's chrome — sidebar and rail, navbar, footer, listing cards, callouts, embed mode; the `ojs-*`/`vm-*` design-system primitives every app is built from are mathviz's `src/css/**`, not here. A rule that targets markup only one page emits (a bespoke SVG diagram, a one-off widget) belongs in a `<style>` block in that page's own `.qmd`, or a `.css` file in the same folder, the same way `apps/polynomial-interpolation/cubic-spline.js` is colocated rather than promoted into mathviz. `apps/distribution-relationships/index.qmd` is the reference: its whole `.ojs-graph-*` block lives in the page. This keeps `styles.css` scannable as the site grows, and means deleting a page deletes its styles with it instead of leaving orphaned rules nobody dares remove. Promote a block into `styles.css` only once a second page actually needs it (and into mathviz's `src/css/` only once it is design-system rather than site chrome). Page-local CSS is **not** exempt from the token rule below — it consumes the same `--vm-*` custom properties, so a colocated block still re-themes with the site.
- Interactive pages reuse mathviz's design-system CSS classes (`ojs-panel`, `ojs-row`, `ojs-grid`, `ojs-fill`, `ojs-auto`, `ojs-table-container`, `ojs-table-toolbar`, `plotly-box-large`) rather than ad hoc per-page styling. `ojs-panel` is chrome only; `ojs-row`/`ojs-grid` are layout only — combine them (`class="ojs-panel ojs-row"`) for a standalone panel, or nest a bare `ojs-row`/`ojs-grid` inside an `ojs-panel` for a control group within a larger panel. Attach `ojs-fill`/`ojs-auto` via `classList.add` on an `Inputs.*` wrapper div to make it fill its row or keep its natural width, instead of setting `el.style` directly.
- **Observable Inputs injects its own `.oi-<hash>` rules into `<head>` at runtime**, i.e. *after* every stylesheet in the cascade (mathviz's included). Any rule of this project's that targets one of those generated forms and ties on specificity therefore **loses**, silently and only in the browser. A bare single-class selector (`.vm-has-play { flex-wrap: wrap }`) is exactly such a tie — it computed to `nowrap` and squeezed slider tracks to 0px. When styling an Observable-generated form, either out-specify it (add the scoping `.ojs-panel`/`.ojs-chart-controls` class plus `form[class^="oi-"]`, as every rule in that part of the file does) or use `!important` (the established idiom here — see the `flex: none !important` on the number spinner). Don't assume a class you invented is safe just because nothing else in `styles.css` defines it.
- **`npm run verify` asserts rendered layout, not just an empty error console** (`checkSliderControls` in `scripts/verify-pages.mjs`): every visible slider's track must be at least 100px wide **and** at least 35% of its own control, and every playback popover must actually paint at its own coordinates. Both thresholds are derived from measuring all 24 sliders on the site (narrowest legitimate: 147px at 49% of its form; the regressions measured 0px and 14%), so each sits about a third below the narrowest real value — re-measure rather than lower one if a genuinely narrower control is ever added. The ratio is the half that catches a track squeezed by a label or readout, and unlike a pixel count it doesn't move with the viewport. Both bugs above are invisible to an error-console check — nothing throws, the page just renders wrong — so these assertions are the regression guard for the whole class. They test the outcome rather than the CSS meant to produce it, so they survive an Observable Inputs upgrade or a refactor of `styles.css`. Both were confirmed to fail when their bug is reintroduced; keep them that way rather than loosening a threshold to make a failure go away.
- Observable Inputs renders every control as `<form class="oi-...">` with its label and control as flex-row siblings; mathviz's `panel.css` overrides this to stack the label above the control instead (`.ojs-panel form[class^="oi-"] { flex-direction: column; ... }`), so that when a label wraps to more lines than its neighbor's (a narrow `.ojs-grid` column, a long parameter name), the control still bottom-aligns consistently across a shared `.ojs-row`/`.ojs-grid` — with label-beside-control, a taller-wrapped neighbor left the shorter field's control vertically off from the others. `.ojs-panel input[type="text"]`'s default width (10em) is sized for the short scalar values most fields hold (an endpoint, a seed, a max-iteration count); a field that genuinely needs to hold a long formula (`fText`, `gText`, `y' = f(t, y)`) opts into `.ojs-fill` instead of relying on a wide default — every existing formula field already does this, so don't widen the default itself to accommodate one.
- Keep each page's logic in small named OJS cells (`result`, `setup`, `mainPlot`, `iteratesPlot`, `convergencePlot`, `iterationTable`) rather than one large cell, and keep the same cell names/shapes across method pages for consistency.
- Prefer explicit `for`/`while` loops and `if`/`else` over `.map()/.filter()/.reduce()` chains and ternaries in OJS cells and `js/report-bug.js` (and in mathviz's `src/js/**`, which follows the same rule) — this codebase is read by a Python-oriented audience, and imperative control flow reads more naturally to them than JS-functional chains. Callbacks required by an API (Plotly config values, `Plot` accessors, `addEventListener`) are fine to keep; clean up their bodies per the same rule if they contain a chain/ternary. Stateful closures that exist for a real reason (e.g. `mainPlot`'s `_plotDiv` reuse) are not a style violation and shouldn't be "fixed."
